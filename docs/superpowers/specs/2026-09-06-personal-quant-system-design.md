# 个人量化交易系统 · 设计文档

- **日期**：2026-09-06
- **状态**：设计已确认，待编写实施计划
- **范围**：本文档描述系统的完整目标形态（六期）。实施计划仅覆盖**一期**。

---

## 1. 背景与目标

### 1.1 现状

当前链路依赖聚宽平台：

```
聚宽（数据 + 回测 + 策略运行时 + 模拟盘信号）
    → Redis → 云 Windows → miniQMT → 实盘下单
```

后半段（Redis → Windows → miniQMT）已跑通并经实盘验证，是既有资产，本项目**保留其形状，只做规范化**（协议定义、幂等、断线恢复、对账），不重写。

### 1.2 要解决的问题

聚宽的四个结构性限制：

1. **接不了另类数据** —— 新闻事件、研报、龙虎榜、北向资金、解禁、资金流等无法接入
2. **回测引擎改不了** —— 撮合、滑点、费用模型是黑盒，无法调整为符合自身实盘经验的形态
3. **因子/模型算力受限** —— 机器学习、大规模因子挖掘、第三方库在平台上跑不动或不允许
4. **多系统拼接脆弱** —— 跨多个系统，出问题无法定位、无法对账、无法回溯；且存在平台限流或停服风险

### 1.3 目标

自建完整系统替代聚宽，前半段（数据、策略、回测、运行时）全部自主可控，后半段沿用并规范化。

**非目标（一期）**：美股与币圈的实际接入、日内高频策略、分钟级精细撮合。

## 2.1 数据粒度决策的修订（2026-09-08）

原决策 3「日线为主，分钟线按需」是在**未见过真实策略**的前提下做出的。

引入首个真实策略（首板高开/低开，`Structural Strategy V1.2`）后该假设失效——该策略需要：

| 时点 | 需要 | 日线能否满足 |
|---|---|---|
| 09:26 入场 | 集合竞价价格 | ✅ 竞价成交价即当日 `open`（已实测验证相等） |
| 09:26 入场 | 集合竞价**成交量** | ❌ 需分钟线首根 |
| 11:25 / 14:25 / 14:50 出场 | 日内实时价与涨停价 | ❌ 需分钟线 |
| 每日盘前 | 全市场涨停数 / 炸板率 / 连板高度 / 中位收益 | ✅ 全市场日线可派生 |
| 入场筛选 | 市值 / 流通市值 / 换手率 | ❌ 需估值表 |

**修订后的决策：**

1. **日线仍是主数据**，覆盖全市场、多年，由 Linux 独立采集
2. **分钟线是策略必需数据**（不再是「按需」），但只覆盖**候选股在候选日**——不需要全市场全历史
3. 分钟线来源为 Windows 侧 QMT，异步同步到 Linux（见 §3.2 原则二修订）
4. 新增**估值表**与**市场生态因子表**

**为什么分钟线不需要全市场**：候选池是「昨日首板涨停股」，先用日线扫出候选（每日约 30–80 只），再只对这些 (标的, 日期) 对取分钟线。数量级从 5400 只 × 900 日降到约 3–7 万个组合。

## 3. 系统架构

### 3.1 部署拓扑

```
┌─── Mac（开发机）───┐
│  写代码、本地调试   │
│  小规模本地回测     │
└──────┬─────────────┘
       │ git / 部署
       ▼
┌─── 云 Linux（核心 + Web）── 24×7 ────────────────────────┐
│  数据仓库 · 采集调度 · 因子计算 · 回测 · 策略运行 · 风控  │
│  FastAPI 服务 · RQ 任务队列                               │
└──────┬───────────────────────────────────────────────────┘
       │ Redis（Stream）
       ▼
┌─── 云 Windows（执行代理）── 24×7 ───┐
│  xtquant 薄封装：接单/下单/回报/查询 │
└──────────────────────────────────────┘
```

### 3.2 三条架构原则

**原则一：Windows 侧不放任何策略逻辑。**

Windows 环境难调试、难测试、难复现。执行代理只做一件事：把标准化订单指令翻译成 `xtquant` 调用，把回报翻译回标准化事件。所有决策、风控、状态推演都在 Linux 核心侧。执行代理的代码量应小到可一眼读完。

**原则二：核心节点的研究能力不依赖 Windows 在线。**（2026-09-08 修订）

日线与派生数据仍由 Linux 独立采集（mootdx / AKShare，纯 HTTP，跨平台），研究不受执行链路可用性影响。

**修订**：历史分钟线免费源不可得（见 §2.1），只能由 Windows 侧的 QMT `xtdata.download_history_data` 下载。为保住本原则，采用**异步同步**而非在线依赖：Windows 定时下载并落盘，Linux 定时拉取。Linux 侧研究读的始终是本地副本，Windows 离线时数据只是变旧，研究不中断。

**原则三：回测与实盘是同一套代码的两种 Broker 实现。**

不存在"回测系统"和"实盘系统"两个系统。差异只可能来自 `Broker` 这一个明确边界，因而可以逐笔归因。这是对"多系统拼接、出问题无法定位"的正面回答。

### 3.3 部署约束

- **云 Linux 必须在境内**。AKShare / mootdx / efinance 背后是国内行情与财经站点，境外服务器会遇到延迟、限流或不通。
- Linux 与 Windows 若同厂商同区域，Redis 走内网；否则必须 TLS + 强密码 + IP 白名单，禁止裸奔公网。

### 3.4 模块划分

```
core/          内核 — 不认识任何市场、任何数据源
  clock          BacktestClock（历史推进）/ LiveClock（真实时钟）
  calendar       TradingCalendar 抽象 — AShare / 未来 Crypto(24×7)
  types          Symbol / Bar / Order / Fill / Position
  portfolio      账户与持仓模型，交易约束可插拔
  constraints    T+1 / 涨跌停 / 停牌 / 整手 / 做空 等约束实现
  events         事件类型与事件循环

data/          数据层 — 项目最大工作量模块
  providers      数据源适配器：mootdx / akshare / efinance / qmt …
  storage        Parquet 分区 + DuckDB 查询层
  pipeline       采集调度、增量更新、复权因子计算、PIT 对齐
  quality        质量校验规则与报告
  feed           DataFeed 抽象：HistoricalFeed / LiveFeed

strategy/      策略基类 + ctx 显式注入 + 因子库
backtest/      SimBroker 撮合 + 回测驱动器 + 绩效分析
execution/     Broker 抽象 + Redis 客户端 + 风控闸门
web/           FastAPI + HTMX 服务、RQ 任务队列
agent/         ← 部署到 Windows 的执行代理（独立打包）
ops/           对账、心跳、告警、每日报告
```

`core/` 的纯净度是多市场预留的全部成本：它只认识"约束"这个概念，不认识"涨跌停"这条具体规则。

## 4. 数据层

### 4.1 存储选型：Parquet + DuckDB

日线全 A 十年约 1300 万行、几百 MB，DuckDB 单机扫描秒级。

- **零运维** —— 无服务进程，仓库即文件，可备份、可整体迁移
- **列存 + 谓词下推** —— 因子计算友好，取少数字段不读全表
- **可平滑升级** —— 三期向量化引擎换 polars 时读的仍是同一批 Parquet

不选 PostgreSQL/TimescaleDB（行存，全市场因子扫描慢，需运维）；不选 ClickHouse（能力过剩，运维成本换不回收益）。

### 4.2 四张地基表

| 表 | 内容 | 可变性 |
|---|---|---|
| `instruments` | 标的主表：代码、名称、上市日、**退市日**、板块、ST 历史、代码变更史 | 追加 + 修订 |
| `bars_daily` | **不复权** OHLCV 事实表 | **只追加，永不重写** |
| `adj_factors` | 复权因子，由分红送转数据计算 | **可随时重算** |
| `fundamentals` | 财务数据，主键 `(symbol, report_period, ann_date)` | 追加（同期可多版本） |

**行情与复权因子分离，使"数据腐烂"在结构上不可能发生。** 前复权序列每次分红都会整体变化，一旦落盘即开始腐烂且不易察觉。分离后：事实表不变，因子可重算，任意历史时点的复权价都能精确重现，回测结果可复现。

`fundamentals` 允许同一报告期多行（业绩预告 / 快报 / 正式 / 更正），每行带自己的 `ann_date`——这是 PIT 的物理基础。

### 4.3 目录布局

```
warehouse/
  instruments.parquet
  bars_daily/            year=YYYY/part.parquet
  bars_1min/             symbol_group=.../year=YYYY/     # 五期，仅候选池
  adj_factors/
  corporate_actions/     分红送转、代码变更、停复牌
  fundamentals/          report_type=.../year=YYYY/
  universe_snapshots/    date=YYYY-MM-DD/
  alt/                   dragon_tiger/ northbound/ reports/ news/   # 四期
  ingest_log/            采集日志：数据集、日期、源、时间、成败
```

### 4.4 PIT 访问契约

数据层对外**只暴露带 `as_of` 语义的接口**：

```python
feed.get(symbols, fields, start, end, as_of=T)   # 只返回 T 时刻可见的数据
```

回测引擎调用时 `as_of` 恒等于当前 bar 时间。**未来函数从 API 层面被堵死，而非依赖策略作者自觉。** 未来函数是回测失真的头号原因，且几乎总是无意引入。

### 4.5 股票池：规则化定义

免费数据源缺少指数成分股历史快照。做法是绕开它，用规则定义股票池：

```
universe(T) = instruments 中 T 日已上市且未退市
            − 上市不满 N 日（次新股噪声）
            − 当日 ST / *ST
            − 当日停牌
            − 流动性过滤（近 20 日均成交额 < 阈值）
            − 市值分位过滤（可选）
```

每日落盘快照，回测直接读快照。比追踪指数成分股更可控、更可复现，且不依赖第三方数据。

**股票池在历史每一天都必须包含当时仍在市的全部股票**，否则幸存者偏差会使回测系统性虚高。

### 4.6 数据质量校验（六类规则）

全免费方案的对价。**任何 blocking 级问题阻止该批数据进入回测可用集。**

| # | 规则 | 期次 |
|---|---|---|
| 1 | **完整性** —— 交易日历上每交易日每只在池股票应有 bar；缺失须有停牌记录解释 | 一期 |
| 2 | **越界** —— 非 ST 非新股涨跌幅 > 10%（ST 5%、双创 20%） | 一期 |
| 3 | **内部一致性** —— `low ≤ open, close ≤ high`；`volume = 0` 必须对应停牌 | 一期 |
| 4 | **交叉源比对** —— mootdx / AKShare / QMT 收盘价差异超阈值告警 | 二期 |
| 5 | **复权自洽** —— 除权日前后用因子还原后，收益率序列连续无跳变 | 二期 |
| 6 | **财务勾稽** —— 资产 = 负债 + 权益；同报告期多版本修订幅度告警 | 二期 |

每日产出质量报告，纳入告警链路。

### 4.7 采集调度

- **增量为主**：每日收盘后拉当日；历史数据一次性回填
- **幂等**：同日重跑结果一致，靠 `(dataset, date)` 主键覆盖写
- **可追溯**：`ingest_log` 记录哪天、哪个源、何时采、成败，数据出问题时可回溯
- **源可替换**：provider 统一接口，免费源接口变更或失效时整体换源，不影响上层

## 5. 内核与策略层

### 5.1 事件循环

一套 `EventLoop`，事件来源由 `Clock` 决定：

| Clock | 事件来源 | 时间推进 |
|---|---|---|
| `BacktestClock` | `HistoricalFeed` 按序泵出 | 由数据推进 |
| `LiveClock` | QMT 行情推送 / 轮询 | 由真实时钟推进 |

事件类型：`SessionStart` / `Bar` / `Timer` / `OrderSubmitted` / `Fill` / `Reject` / `SessionEnd`。

策略代码对两种 Clock 完全无感 —— 实盘跑的是回测验证过的同一条代码路径。

### 5.2 策略生命周期

```python
class Strategy:
    def on_init(self, ctx):          ...  # 一次性：声明参数、注册因子、订阅数据
    def on_session_start(self, ctx): ...  # 每日盘前：选股、算目标仓位
    def on_bar(self, ctx, bars):     ...  # 主逻辑
    def on_fill(self, ctx, fill):    ...  # 成交回报
    def on_session_end(self, ctx):   ...  # 收盘后：记录、复盘
```

**`ctx` 为显式注入的运行时上下文，不使用全局变量：**

```
ctx.now         当前时间（来自 Clock）
ctx.data        PIT 数据访问，as_of 自动绑定到 ctx.now
ctx.portfolio   只读持仓视图
ctx.order       下单接口
ctx.params      策略参数
ctx.state       策略持久化状态
ctx.log         结构化日志
```

显式注入换来两项收益：**策略可单元测试**（注入假 ctx，断言下单意图，无需跑回测）；**多策略并行不互相污染状态**。

### 5.3 交易约束：多市场预留的全部成本

`Portfolio` 本身不知道 T+1 是什么，它持有一组可插拔约束：

```python
# A 股
constraints = [
    T1SettlementConstraint(),    # 当日买入不可卖出
    PriceLimitConstraint(),      # 涨跌停不可成交
    SuspensionConstraint(),      # 停牌不可交易
    LotSizeConstraint(lot=100),  # 整手
    NoShortConstraint(),         # 不可做空
]

# 币圈（六期）
constraints = [LeverageConstraint(max=3), MinNotionalConstraint()]
```

**这组约束在两处共用同一份代码**：回测时 `SimBroker` 撮合前检查，实盘时风控闸门下单前检查。因此回测对"此单能否成交"的判断与实盘完全一致。

### 5.4 下单抽象

```python
ctx.order.submit(symbol, side, qty, type, price)   # 低层：精确控制
ctx.order.target_weight(symbol, 0.05)              # 高层：目标权重
ctx.order.target_value(symbol, 50000)              # 高层：目标市值
```

高层在内部转为低层，转换过程（整手取整、可用资金检查、可卖数量检查、涨跌停过滤）走上述约束系统。回测与实盘共用同一套转换逻辑。

### 5.5 因子作为一等公民

```python
class Factor:
    def compute(self, universe, as_of) -> Series: ...
```

三个特性：

- **声明式依赖** —— 因子可依赖其它因子，自动拓扑排序
- **自动缓存** —— `(factor_id, date, universe_hash)` 只计算一次，落盘复用
- **PIT 强制** —— 因子只能通过 `as_of` 接口取数

三期的向量化研究引擎**重用同一套 Factor 抽象**，仅更换批量执行后端，以保证两条路径算出的因子值一致。

## 6. Broker 的两种实现

回测层与执行层是 `Broker` 接口的两个实现。二者的约束与转换逻辑必须共享，分开设计必然漂移。

### 6.1 SimBroker（回测撮合）

**撮合模型分级，可配置：**

| 级别 | 行为 | 用途 |
|---|---|---|
| 理想 | 指定价格全额成交 | 因子粗筛、快速迭代 |
| **保守（默认）** | 下一根 bar 开盘价成交 + 涨跌停/停牌拦截 + 成交量占比上限 | 正式回测 |
| 精细（五期） | 用分钟线做 VWAP/TWAP 拆单模拟 | 容量测试、执行优化 |

保守模式的成交量约束：单笔成交不超过当根 bar 成交量的 X%（默认 5%），超出部分顺延或撤单。**此约束对小市值策略是生死线**——缺失会使回测买到实际买不到的量。

**不可妥协的正确性原则：信号在 bar T 生成，成交在 bar T+1。** 绝不允许用生成信号那一刻的 bar 数据成交。这是回测虚高的第二大原因（第一是未来函数，已由 `as_of` 契约堵死）。

**三个可插拔模型 —— "引擎可改"卡点在此兑现：**

- **撮合** —— 可为特定策略写专用撮合逻辑
- **滑点** —— 固定点数 / 固定比例 / 按成交额分档 / **基于实盘对账校准的经验模型**（五期）
- **费用** —— 佣金（含最低 5 元）、印花税、过户费、规费，全部可配置。实际费率已知，可做到与实盘一致

### 6.2 QmtBroker（实盘执行）

#### Redis 通道协议

```
cmd:orders     指令队列   Linux → Win   Redis Stream，每条带 client_order_id
cmd:control    控制指令   Linux → Win   Redis Stream（启停、撤单、查询）
evt:fills      回报流     Win → Linux   Redis Stream + consumer group
state:account  状态快照   Win → Linux   定期全量写入持仓/资金
```

**必须用 Stream，不得用 pub/sub。** pub/sub 断线即丢且不可追溯；Stream 有持久化与消费确认，核心侧重启后可从上次位置继续消费回报。

**幂等**：`client_order_id` 由核心侧生成，Windows 侧维护已处理 ID 集合，重复指令直接忽略并回放旧结果。**网络重传永不导致重复下单。**

#### 风控闸门（核心侧，下单前）

- 单票仓位上限 / 单日换手上限 / 单日最大亏损熔断
- 订单价格偏离度检查（防参数错误下出离谱价格）
- 交易时段检查、可用资金与可卖数量检查
- **全局 kill switch**

**kill switch 必须有一条不依赖 Web 的独立路径**（直接写 Redis key，或一个独立极简脚本）。Web 故障不得导致无法停机。

#### 三层对账

| 层 | 内容 | 频率 |
|---|---|---|
| 盘中对账 | `state:account` 快照 vs 核心侧推演持仓，不一致**立即停止下单**并告警 | 每 N 分钟 |
| 盘后对账 | 核心侧订单簿 / Windows 实际成交 / 券商对账单逐笔比对 | 每日 |
| **回测-实盘对账** | 同策略同交易日，`SimBroker` 模拟成交 vs 实盘真实成交，**差异须能被滑点模型解释**；差异数据反哺滑点模型校准 | 每日 |

第三层是本架构独有能力，使回测随实盘运行持续变准。一期即埋好数据采集，五期建模。

#### 故障处理矩阵

| 故障 | 行为 |
|---|---|
| Redis 不可达 | 核心侧停止发单并告警；在途订单由 Windows 侧自主管理至终态 |
| Windows agent 崩溃 | 心跳超时告警；重启后从 Stream 恢复未确认指令，靠幂等防重复 |
| xtquant 断连 | Agent 自动重连，期间指令排队不丢；超时未恢复则告警 |
| 持仓不一致 | **立即停止下单**，转人工介入 |
| 数据质量 blocking | 当日不生成信号并告警（宁可不交易，不可用脏数据交易） |

## 7. Web 层

### 7.1 访问方式与安全

**Web 服务只监听内网，通过 Tailscale（或 WireGuard）私有网络访问。** 手机安装客户端即可随时访问，而对公网完全不可见。不可达的系统无需防守。

在此之上仍需：

- 登录认证 + TOTP 二次验证（防设备丢失）
- 所有写操作审计留痕（谁、何时、做了什么）
- 危险操作（启停策略、手动下单、修改风控参数）二次确认

### 7.2 任务队列

回测是长任务，网页不能同步等待。采用 **RQ + Redis**（Redis 已有；RQ 比 Celery 简单一个数量级，个人系统足够）。

- 任务状态、进度、日志通过 SSE 推送前端
- 回测结果落盘并按 `run_id` 归档，可检索、可对比

### 7.3 技术栈

**FastAPI + HTMX + ECharts + Tailwind**。服务端渲染 + HTMX 局部刷新，ECharts 绘制 K 线 / 净值 / 因子分布。系统 90% 的界面是表格、表单、图表，无复杂客户端状态，无需维护前端构建链与前后端两套数据模型。FastAPI 与已选的 pydantic 原生集成。

### 7.4 Mac 本地开发的数据获取

数据仓库位于云上。Linux 侧提供数据子集导出（如最近两年 + 指定股票池），Mac 用 rsync 拉取用于本地调试。**全量数据不下载**，本地只需满足单元测试与小规模验证。

### 7.5 Web 功能分期

| 期 | Web 增量 |
|---|---|
| 一期 | **只读监控台**：持仓、净值、当日信号、成交、三层对账结果、数据质量报告 |
| 二期 | 回测任务提交 + 结果查看 + 多次回测对比 |
| 三期 | 因子研究界面：IC 曲线、分层回测、因子相关性 |
| 四期 | 策略控制：启停、参数调整、审计日志 |
| 五期 | 执行分析：滑点归因、成交明细 |

一期只读监控台工作量不大但价值高 —— 它是观察影子模式与实盘的眼睛。

## 8. 测试与验证

### 8.1 测试分层

| 层 | 测什么 | 特点 |
|---|---|---|
| 单元 | `core/` 类型、每个 `Constraint`、`Portfolio` 推演 | 毫秒级，数量最多 |
| 数据层 | **质量校验规则本身** —— 构造脏数据，断言被捕获 | 校验器也是代码，也会错 |
| 策略 | 注入假 `ctx`，断言下单意图 | 毫秒级，不跑回测 |
| 回测引擎 | 正确性验证，见 8.2 | 项目最关键的测试 |
| 集成 | 假 Redis + 假 xtquant，端到端跑一个完整交易日 | 验证链路 |
| 影子模式 | 实盘逻辑全跑，**只记录意图不下单** | 上实盘前最后一道闸，**跑满一周** |

### 8.2 回测引擎正确性：三条腿

#### 第一腿：合成数据断言

构造已知答案的价格序列，手算预期结果，断言引擎输出**精确匹配到分**：

- 10 天每天涨 1%，买入持有 → 净值等于手算值
- 除权日前后 → 复权收益率连续，账户市值不跳变
- 涨停日买入 → 必须不成交
- 停牌期间 → 持仓保持、不产生成交
- T+1：当日买入当日卖出 → 必须被拒绝
- 成交量占比超限 → 部分成交并顺延

每个边界场景一条断言。这些测试是敢用该引擎下真钱的唯一理由。

#### 第二腿：聚宽交叉验证（主要验证手段）

已有聚宽策略与自建系统同市场、同规则体系，比通用引擎参照干净得多。**必须分层控制变量**，否则只能得到"净值差 2%"这类无法行动的结论。

**第一层 —— 先比数据，不比策略。** 同批股票、同时间段，导出聚宽的复权价 / 成交量 / 财务数据，与自建仓库逐字段比对。**此步必须先完成**：数据未对齐时，任何净值差异都无法归因。这一步同时是对全免费数据源质量的权威体检，直接验证 4.6 的六类规则是否充分。

**第二层 —— 固定数据，只比引擎（最关键）。** 将聚宽导出的数据喂给自建引擎运行，数据变量被完全消除，净值差异纯粹来自撮合逻辑、费用口径、成交时点。差异须逐项拆解：

| 差异来源 | 排查方式 |
|---|---|
| 成交时点 | 聚宽默认在哪根 bar 成交？对齐"T 信号 / T+1 开盘成交" |
| 费用口径 | 佣金最低 5 元、印花税、过户费逐项对齐 |
| 涨跌停判定 | 聚宽用何价判涨停？是否允许涨停板买入 |
| 成交量约束 | 聚宽默认有无成交量占比限制 |
| 复权口径 | 前复权基准日不同会导致净值曲线整体缩放 |

**残差须收敛到可解释范围，否则引擎不通过验收。**

**第三层 —— 各用各的数据。** 此时差异应约等于第一层数据差异 + 第二层引擎差异。能对上说明对系统的理解准确；对不上说明仍有未识别变量。

**验证基准策略**：挑选 2–3 个有代表性的聚宽策略，**手工在新 API 上重写**（不做兼容层），固化进测试套件，每次修改引擎都重跑。选取标准是覆盖不同机制：

1. 日频调仓的多标的策略 —— 测组合再平衡
2. 带止损的择时策略 —— 测条件单与 T+1
3. 持仓周期长的策略 —— 测除权除息处理

重写过程本身也是对新 API 易用性的第一次真实检验。

#### 第三腿：实盘回放对账

即 6.2 的第三层对账。这条是活的，随实盘运行持续验证并改进滑点模型。

### 8.3 未来函数专项测试

**故意编写偷看未来的策略**（用次日收盘价做当日决策），断言 `as_of` 契约使其**取不到数据或直接抛异常**。

正向测试只能证明"正常用法能取到数据"，反向测试才能证明"错误用法被堵死"。

### 8.4 回测可复现

```
run_id = hash(git_commit + data_snapshot_version + params_hash)
```

数据仓库每日快照有版本，代码有 commit，参数有配置哈希。**任何一次回测结果都能精确重跑。**

缺少此机制时，多轮参数迭代后无法判断净值提升来自策略改进还是数据变化 —— 这种自欺欺人会把过拟合当作 alpha 拿去下真钱。

## 9. 可观测性与运维

- **结构化日志**（structlog）—— 每个决策点记录：时间、策略、输入数据哈希、输出订单意图、每条约束的检查结果。可完整重放决策过程
- **每日运行报告** —— 数据质量 + 信号生成 + 下单执行 + 三层对账结果，汇总推送
- **双向心跳** —— 核心侧与 Windows agent 互相心跳，任一侧失联告警
- **回测归档** —— 每次回测的 `run_id`、参数、结果、净值曲线全部落盘，可检索、可对比

## 10. 分期路线图

每一期都是纵切片：结束时都有一个能跑实盘的系统，能力递增。

### 一期 · 最小实盘闭环 ★ 核心

**目标：一个价量策略，从本地数据 → 回测 → 影子一周 → 真实下单，全链路打通。**

| 模块 | 一期范围 |
|---|---|
| `core/` | Clock、A 股 Calendar、核心类型、Portfolio + 五条约束、EventLoop |
| `data/` | `instruments` / `bars_daily` / `adj_factors` 三表；mootdx + AKShare provider；**`as_of` 契约**；质量校验规则 1–3 |
| `strategy/` | Strategy 基类 + `ctx` 显式注入 |
| `backtest/` | SimBroker 保守撮合 + 完整费用模型 + 基础绩效指标 |
| `execution/` | Redis Stream 协议 + 风控闸门 + kill switch + Windows agent |
| `web/` | 只读监控台 |
| `ops/` | 三层对账 + 结构化日志 + 每日报告 |
| 验证 | 合成数据断言套件 + 聚宽交叉验证第一、二层 + 未来函数专项测试 |

**关键取舍：一期策略只用价量，不碰财务数据。** 将 PIT 财务这块最复杂的工作推到二期。但 `as_of` 契约必须一期建好 —— 它是全系统地基，后补等于重写。

**验收标准**（须全部满足）：

1. 合成数据断言套件全绿
2. 聚宽交叉验证第二层残差可逐项解释
3. 未来函数专项测试通过
4. 影子模式连续跑满一周无中断、无告警
5. 三层对账连续一周零不一致
6. 用小资金完成至少一轮真实开仓平仓

### 二期 · 因子与财务数据

`fundamentals` 表 + PIT 对齐 · Factor 抽象与缓存 · 规则化股票池 + 每日快照 · 质量校验规则 4–6 · 绩效归因 · Web 回测任务提交与结果对比

**验收**：跑通一个多因子选股策略；聚宽交叉验证第三层残差可解释。

### 三期 · 向量化研究引擎

批量因子计算后端 · **与事件驱动引擎的一致性测试**（同一因子两条路径算出的值必须一致）· 因子评价体系（IC、IR、分层回测、换手率、衰减）· Web 因子研究界面

**验收**：全市场十年单因子扫描进入分钟级；一致性测试全绿。

### 四期 · 另类数据层

龙虎榜 · 北向资金 · 研报 · 新闻事件 · 解禁 · 资金流 · 行业轮动 · Web 策略控制与审计

**验收**：至少一个事件驱动策略跑通回测并进入影子模式。

### 五期 · 执行优化

分钟线落盘 · VWAP/TWAP 拆单 · **用一至四期积累的对账数据校准滑点模型** · Web 执行分析

**验收**：滑点模型对实盘成交的预测误差收敛到目标区间。

### 六期 · 多市场扩展

币圈（CCXT，验证多市场抽象）→ 美股。

**验收**：`core/` 无需修改，仅新增 Calendar + 约束组 + Broker 即完成接入。

### 工作量说明

不给周数 —— 取决于实际投入时间。相对工作量约为 **一期 ≈ 二期 + 三期之和**，因一期需同时立起内核、数据地基与实盘链路。这是纵切片的必然代价，也是其价值所在：一期结束即有真金在跑。

## 12. 风险与已知取舍

| 风险 | 缓解 |
|---|---|
| 免费数据源接口变更或失效 | provider 统一接口可整体换源；六类质量校验可及时发现异常；`ingest_log` 可回溯 |
| 免费数据 PIT 正确性不如商业源 | 聚宽交叉验证第一层作为权威体检；财务数据存 `(report_period, ann_date)` 三元组 |
| 缺少指数成分股历史 | 规则化股票池绕开；同时从项目启动日起每日落盘快照，时间会补上历史 |
| ~~**指数因子缺失**~~ | 已在计划 2-2a 解决：指数走 mootdx 的 `index()`（个股 `bars()` 取不到指数），沪深300 覆盖 954 天，`index_ma20_slope_5d` 894/894 天非空 |
| 云 Linux 与云 Windows 跨机通信故障 | Redis Stream 持久化 + 幂等 + 故障处理矩阵 + 双向心跳 |
| Web 可操作真钱，存在安全风险 | 私有网络访问 + TOTP + 审计留痕 + 危险操作二次确认 + 独立 kill switch 路径 |
| 一期工作量大，可能中途失去动力 | 纵切片保证一期结束即有可用系统；一期内部亦可按"数据→回测→影子→实盘"逐步见到成果 |
| 自建引擎正确性 | 三条腿验证；未通过验收不得投入真金 |
| ~~**历史分钟线免费源不可得**~~ | 已在计划 2-1b 打通：Windows 侧 QMT `download_history_data` 按标的整年下载 0.69s/只，导出候选日 parquet 回传 Linux。跨源验证（QMT 分钟 vs mootdx 日线）1,320 个股-日零差异 |
| **QMT 分钟线只有约一年且是滚动窗口** | 2026-09-09 实测最早 2025-09-09，共 242 个交易日；同账户日线却能回到 2023-01，故非权限问题。**后果一**：精确版策略只能覆盖 894 个交易日中的 242 个（27%），其余区间只能用日线近似版。**后果二（有时效）**：每过一天永久丢一天，必须建立**每日增量归档**，且 2025-09-09 之前的已不可追回 |
| **Linux 核心节点内存仅 1.9 GB** | 可用约 870 MB，且已跑 nginx/docker/chrome。全 A 十年回测大概率 OOM。需扩容或分批处理；回测 worker 必须独立进程以隔离 OOM |
| ~~**历史估值数据缺口**~~ | 已在计划 2-1c 解决：QMT 财务表 `Capital` 提供事件级股本历史（219,154 条 / 5,799 只，中位 36 条/只），市值 = 收盘价 × 股本。**覆盖 100% 的日线行**（4,504,869 行，2023-01 至今）。校验：恒等式 0 违反、流通>总市值 0 行、换手率>100% 0 行 |
| **免费分红源不含配股** | `stock_fhps_detail_em` 只有分红送转。做过配股的标的复权因子会偏差，直接影响回测收益率。二期须补配股数据源；质量规则 5（复权自洽）可在除权日附近抓到这类跳变 |
| **在市股票缺上市日期** | 免费源不提供 `list_date`（实测 5560/5921 为空）。但策略的 `filter_new_stock(days=50)` 只需区分「上市不足 50 天」，**可用日线首个 bar 的日期完全替代**——近 50 天上市的标的其首根日线必在库内 |
| ~~**mootdx 单次回溯上限约 3.2 年**~~ | 已在计划 2-1a 解决：`start` 参数分页，实测 600036.SH 自 2023-01 取到 893 行且无截断。截断告警语义收紧为「翻满 max_pages 仍未覆盖」 |
| **mootdx 不提供退市股历史** | 2-1a 试跑实测：三板块 5550 只中 333 只已退市（2023 年后退市 145 只），mootdx 对其一律返回空。采集侧已保留退市股不做剔除，但数据源拿不到，全市场扫描仍残留约 2.7% 的幸存者偏差。首板策略通常本就排除 ST，影响有限，但与聚宽交叉验证时需按此解释差异 |
| **估值接口依赖东财，易被代理/网络拒绝** | 2-1a 试跑中 `stock_zh_a_spot_em` 在 Mac 上遭 ProxyError。采集脚本已把估值步骤降级为可失败：它取不到不会让已跑数小时的日线采集与派生数据白费 |
