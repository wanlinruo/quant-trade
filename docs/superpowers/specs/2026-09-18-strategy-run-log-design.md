# 策略运行日志：让影子盘与模拟盘说得清每天跑了什么

创建日期：2026-09-18
状态：已实现并通过全仓测试

---

## 一、为什么做

2026-09-18，用户反馈：「模拟交易和影子盘我都看不到运行日志，我都不知道具体策略
交易的策略运行情况，完全无任何记录，即使是空仓也应该有运行日志吧」。

核查属实。两个运行时当天各自只留下这些痕迹：

| 来源 | 内容 |
|---|---|
| 影子盘 `live_events` | `session_start 完成`；`auction 事件已过期，未补跑` |
| 模拟盘 `paper_events` | `session_start 完成`；`auction 完成` |
| 模拟盘 `paper_logs` | 4 条行情中断告警 |
| 页面 | 实盘监控页只有净值、持仓、心跳；模拟盘只有账户列表与净值曲线 |

**为什么空仓、扫了多少票、卡在哪个条件上，一概没有。**

同一天还暴露了它的代价：Windows 执行代理 05:06 崩溃，影子核心整个上午取不到券商
账户快照，09:30 的竞价事件被记成「事件已过期，未补跑」——页面上看不出任何异常，
直到人工登录服务器翻 SQLite 才发现当天一笔决策都没做。

值得注意的是，**数据本来就有**：结构化策略的 `StructuralSelection.decisions` 里
每只候选都有 `tag`/`state`/`reason`/`allow`，跑完即丢，从未落盘。

## 二、目标与非目标

**目标**

1. 每个策略事件都留下一条可读记录，**空仓、无候选、提前返回同样要有**；
2. 记录能回答「为什么没买」——候选池多少、通过多少、被拒原因分布；
3. 页面上能按交易日回看，不用登服务器；
4. 记录失败绝不影响交易。

**非目标**

- 不做逐只判定的全量落盘（本轮只做汇总 + 被拒原因聚合）；
- 不做告警（已有的每日服务质检负责「跑没跑」，本设计负责「跑出了什么」）；
- 不改任何交易判定逻辑，不引入推断字段。

## 三、记录结构

两张表，分别落在各自现有的状态库里，结构同构（模拟盘多一列 `account_id`）：

- 影子盘：`var/shadow-state.sqlite3` 的 `live_strategy_runs`
- 模拟盘：`var/workbench/workbench.sqlite3` 的 `paper_strategy_runs`

| 列 | 类型 | 含义 |
|---|---|---|
| `event_key` | TEXT | 主键（模拟盘为 `account_id` + `event_key`），与事件表同键 |
| `session` | TEXT | 交易日 |
| `phase` | TEXT | `session_start` / `auction` / `checkpoint` / `bar` / `session_end` |
| `started_at` / `finished_at` | TEXT | 本次事件的起止时刻 |
| `duration_ms` | INTEGER | 耗时 |
| `cash` / `market_value` / `total_value` | REAL | 事件结束时的账户快照 |
| `position_count` | INTEGER | 持仓只数 |
| `candidates` / `passed` | INTEGER NULL | 候选池只数、通过筛选只数；策略未上报则为 NULL |
| `orders` / `rejects` | INTEGER | 下单意图笔数、被风控拒绝笔数 |
| `summary` | TEXT | 一行中文结论，页面主显示 |
| `reasons_json` | TEXT | 被拒原因聚合，如 `{"高开超过阈值": 12, "竞价量不足": 5}` |
| `note` | TEXT | 没有漏斗时的直白原因，如「没有上一交易日，无从选股」 |
| `error` | TEXT | 事件抛异常时的错误摘要 |

**NULL 的语义必须区分**：`candidates = NULL` 表示「这个策略没有筛选漏斗」（如
`ma_cross`），`candidates = 0` 表示「筛选跑了，候选池是空的」。两者在页面上显示
不同的文案，不得混淆。

**保留**：每个交易日 7~10 行，一年两三千行，全量保留，不做清理。

**幂等**：主键是事件键，同一事件重跑覆盖同一行，与事件表的幂等口径一致。

## 四、上报接口

`Context` 增加 `ctx.report(...)`，一个事件内可多次调用：字段后写覆盖，
`reasons` 按 key 累加。

```python
ctx.report(candidates=37, passed=2, reasons={"高开超过阈值": 12, "竞价量不足": 5})
ctx.report(note="没有上一交易日，无从选股")
```

实现放在 `qsys.ops.strategy_log`：一个可变累加器 `RunReport`，由运行时在事件开始时
创建、注入 `Context`，事件结束时由运行时补齐它知道的部分（起止时刻、耗时、账户
快照、下单意图数、被拒数），合成 `summary` 后交给各自的 store 写入。

**结构化策略要改两处，都不碰交易逻辑**：

1. `StructuralSelection` 把每次 `select()` 的漏斗暴露成 `funnel` 属性——候选池只数、
   路由过的只数、通过的只数、被拒原因计数。数据本就在 `decisions` 里；
2. `StructuralStrategy.on_auction` 选完股后调一次 `ctx.report(...)`；两个提前返回
   分支（`previous is None`、`not picks`）各补一句 `ctx.report(note=...)`。

其他策略不改也有事件级记录，只是没有漏斗。

## 五、写入点与失败隔离

两个运行时各一处，就在现有 `commit_event` 旁边：

- `qsys.live.runtime.LiveRuntime._run_event`
- `qsys.paper.runtime` 的对应事件执行处

**三条硬约束**：

1. **记录失败绝不影响交易**：整个记录过程包在 try/except 内，失败只打日志，
   与 `qsys.ops.services.ServiceRun`「记录失败绝不影响任务本身」同一原则；
2. **事件抛异常也要留记录**：错误摘要写进 `error`，`summary` 写成「事件失败：…」；
   被判定为「已过期，未补跑」的事件同样落一行；
3. **不加推断**：`report` 只接收策略给出的数字与原因文本，运行时不猜原因。

## 六、页面

- 影子盘：实盘监控页在「总览 / 成交 / 对账与质量 / 日报」后加「运行日志」；
- 模拟盘：账户详情页加同名标签。

两边共用同一个模板片段与视图模型：两种存储读出来先转成同一结构，页面只认该结构。

每页顶部是交易日选择（只列有记录的日子，默认最近一天），下面按时间顺序排列：

```
时刻      阶段      结论                              下单/拒单   净值        持仓  耗时
09:15    日初结算   完成日初结算，无策略动作                 —        50,000.00   0    0.3s
09:30    竞价选股   候选 37 只 → 通过 2 只 → 下单 2 笔      2 / 0     50,000.00   0    1.8s
10:30    检查点     持仓 2 只，无卖出条件触发                 —        49,880.00   2    0.4s
```

单行展开显示被拒原因分布与 `note` / `error`。

**空态**：当日无记录时显示「当日没有运行记录」，不得渲染成空表——2026-09-18 早上
正是这种情形，空白会被误读成「跑了但没买」。

## 七、测试

- **累加器**：多次上报的合并语义、原因计数累加、`summary` 的五种形态（有下单 /
  通过 0 只 / 候选 0 只 / 策略无漏斗 / 事件报错）；
- **存储**：写入读回一致；同一事件键重跑覆盖而非追加；
- **运行时**：策略无动作时仍写一行；事件异常写 `error` 行；**注入会抛异常的记录器，
  确认事件照常完成**；
- **结构化策略**：上报的候选数、通过数、原因计数与 `decisions` 一致；两个提前返回
  分支各留 `note`；
- **页面**：两个页面都能渲染；空态文案正确。

## 八、与每日服务质检的关系

不新增质检项。`shadow-core｜当日策略事件已执行` 与 `paper｜当日策略事件已执行`
读事件表，回答「跑没跑」；本设计的记录回答「跑出了什么」。两者不重复告警。
「已过期，未补跑」会同时出现在运行日志里，页面上直接可见。

## 九、上线验证

数字，确认没有漏记或错记；打开两个页面确认渲染与空态。
