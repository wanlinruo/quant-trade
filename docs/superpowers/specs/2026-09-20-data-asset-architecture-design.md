# 数据资产架构、表级血缘与健康模型设计

- 创建日期：2026-09-20
- 状态：需求设计已确认，待分阶段实施
- 目标分支：`feat/data-asset-architecture`
- 基线：`origin/test` @ `3375584f69d254210d5b67a4fe23d09cc7330960`

---

## 一、背景与问题

当前数据层已经具备字段级指标字典、字段血缘、自动验证结果和人工证据，但数据管理页面仍然以
“数据表 / 指标字典 / 数据源”三个相对独立的清单呈现。使用者很难从一张表出发回答以下问题：

1. 这张表为什么存在，服务什么业务；
2. 它是外部事实、确定性派生、参数化因子还是运行记录；
3. 数据最终来自哪些接口，上下游表是谁；
4. 通过什么键、什么基数连接，上下游是否同步；
5. 表、字段和表间关系是否可信；
6. 哪些表适合合并、拆分或保持独立；
7. 历史日线、实时日线、历史分钟、实时分钟、复权因子等核心市场数据在哪里。

更根本的问题是当前物理表较多地反映了采集接口，而不是稳定的市场数据语义。例如
`src/qsys/data/schema.py` 中的 `TUSHARE_DAILY` 同时容纳 OHLC、成交量额、复权因子、
换手率、估值和股本字段；`WarehouseQuery.daily_bars()` 再从中投影八列作为生产日线。
这种方式便于接入单个供应商，但使业务边界、生命周期、质量口径和查询成本被耦合在一张宽表中。

本设计把数据管理从“接口落表清单”升级为“可解释、可验证、可演进的数据资产目录”，并为后续
物理表重构提供不破坏生产消费者的迁移路径。

## 二、当前仓库事实

以下结论来自当前代码，不是目标状态：

- `src/qsys/data/schema.py` 定义约二十余张可写表以及两个只读付费历史数据集；分区表主要按年保存，
  QMT 分钟线已兼容 `year/date` 日分区。
- `tushare_daily` 由 `daily`、`daily_basic` 和 `adj_factor` 三个接口组合得到，包含 28 列。
- 生产 `daily_bars()` 实际只投影 `symbol, dt, open, high, low, close, volume, amount`。
- 历史分钟数据存在 QMT、付费源、Tushare、聚宽等来源；`intraday_bars()` 按显式优先级逐标的选源，
  并保留 `source` 和 `visible_at`。
- 实时行情通过 Redis 请求/响应流和最新状态传递，`get_full_tick` 的全市场快照默认不作为历史事实落盘。
- `src/qsys/data/catalog/` 已登记 `DIRECT / DERIVED / FACTOR` 字段分类、有效期语义、字段血缘、
  验证规则和人工证据。
- `CatalogService` 已能展示指标来源、上下游指标、规则结果和证据，但没有表契约、表级详情、
  表间关系详情或规则定义详情。
- 字段血缘已经可以推导出部分表级主干，例如：
  - `tushare_daily -> price_limits_daily / stock_st_daily -> daily_flags -> market_regime`；
  - `name_history -> delisting_pool -> daily_flags`；
  - `corporate_actions -> adj_factors -> market_regime / strategy`。
- 现有质检结果以指标为目标。Schema、主键、粒度、Join 基数、孤儿行、上下游刷新等表级和关系级
  契约尚未成为页面上的一等实体。

## 三、目标与非目标

### 3.1 目标

1. 以数据表为数据管理主入口，一页看懂用途、粒度、来源、上下游、字段、消费方和健康状态。
2. 按市场语义、数据粒度、更新时间和生命周期建立稳定的规范数据表。
3. 保留来源原始事实用于审计、对账和重放，但不让生产消费者依赖供应商表结构。
4. 明确分离历史定稿数据与实时未定稿状态，杜绝回测或研究静默读到盘中值。
5. 建立字段、表、关系三层质量模型，并通过红、黄、绿、灰角标快速表达健康情况。
6. 基于可重复的静态证据给出合并、拆分、保持独立或证据不足的建议。
7. 通过稳定查询接口和分阶段影子迁移完成改造，不做一次性大切换。

### 3.2 非目标

- 本设计不自动合并、拆分或删除生产表。
- 首版不在网页新增或修改质量规则，只提供可读、可追溯的规则详情。
- 首版不采集查询访问统计；合并/拆分建议只使用契约、血缘、消费者和质量证据。
- 不引入图数据库、湖仓格式或新的前端构建链。
- 不以单一 0–100 分代替质量证据。
- 不在规范层静默混用多个来源，也不在缺失时自动回退到另一个供应商。

## 四、分层模型

```text
外部来源
  -> 原始落地层 Raw
  -> 规范市场数据层 Canonical
  -> 派生指标层 Derived
  -> 策略 / 回测 / 页面

实时行情
  -> 实时状态层 Realtime
  -> 收盘质检与原子发布
  -> 规范历史表

运行记录与质量证据
  -> Operational / Quality
  -> 为以上每层提供可追溯状态
```

### 4.1 原始落地层

- 尽量保持供应商字段和批次边界；仅做解析所需的最小标准化。
- 按 `source / dataset / batch / trade_date` 组织，批次不可原地改写。
- 保存行数、Schema、时间范围、来源、采集时间、校验和和错误摘要。
- 用于审计、第三方对账、重新加工和故障恢复。
- 在数据管理页面默认折叠到“原始层 / 审计”，不与业务规范表并列干扰日常使用。

### 4.2 规范市场数据层

- 以稳定市场概念命名，不以供应商或接口命名。
- 一张表只表达一个业务主题和一种明确粒度。
- 每个主键只保留一个选定真值，来源选择必须显式且可追踪。
- 策略、回测、页面和派生管线只依赖规范查询接口。

### 4.3 实时状态层

- 保存最新报价、当日未完成日线、已完成分钟和当前分钟状态。
- 采用 Redis 状态/流或等价低延迟存储，不与历史 Parquet 混写。
- 任何包含实时状态的查询都必须显式声明 `as_of` 和 `include_live=True`。
- 收盘后通过质量门禁原子发布到规范历史表；发布失败时历史表保持上一版本。

### 4.4 派生指标层

- 只保存由规范事实按确定公式或明确参数口径生成的数据。
- 继续区分无自由参数的 `DERIVED` 和带窗口/口径的 `FACTOR`。
- 每个派生字段必须能够追溯到规范上游字段，并声明重算规则。

### 4.5 运行与质量证据层

- 保存采集运行、发布批次、字段质检、表质检、关系质检和人工证据。
- 运行记录不是市场事实，不与行情表混放。

## 五、目标核心数据集

名称是目标逻辑契约。实施时允许物理路径分阶段切换，但查询层最终只暴露这些稳定概念。

| 数据集 | 主键/粒度 | 主要内容 | 生命周期 |
|---|---|---|---|
| `security_master` | `symbol` | 市场、板块、上市/退市日期等当前基础资料 | 当前快照 |
| `security_name_history` | `symbol, start_date` | 曾用名、有效区间、公告日、原因 | 历史区间 |
| `trading_calendar` | `market, dt` | 开闭市与交易日 | 小型维表 |
| `bar_daily` | `symbol, dt` | 前收、OHLC、成交量、成交额 | 收盘定稿历史 |
| `bar_minute_1m` | `symbol, ts` | 1 分钟 OHLC、成交量、成交额 | 收盘定稿历史 |
| `quote_realtime_latest` | `symbol` | 最新价、盘口、累计量额、行情时间 | 短期实时状态 |
| `bar_daily_realtime` | `symbol, dt` | 当日不断变化的 OHLCVA | 逻辑实时数据集 |
| `bar_minute_realtime` | `symbol, ts` | 已完成分钟及当前分钟状态 | 实时流/状态 |
| `adjustment_factor_daily` | `symbol, dt` | 价格累计因子、股本累计因子 | 历史事实 |
| `corporate_action` | `symbol, ex_date, action_id` | 分红、送转、配股等事件 | 事件历史 |
| `share_capital_history` | `symbol, effective_date` | 总股本、流通股本 | 历史事实 |
| `valuation_daily` | `symbol, dt` | PE、PB、PS、市值、换手率等 | 日度事实 |
| `price_limit_daily` | `symbol, dt` | 前收、涨停价、跌停价 | 日度事实 |
| `security_status_daily` | `symbol, dt` | ST、停复牌、退市整理状态 | 日度状态 |
| `market_flags_daily` | `symbol, dt` | 封板、跌停、触板、炸板、首板等 | 确定性派生 |
| `market_regime_daily` | `dt` | 市场广度、情绪和指数类因子 | 参数化因子 |

### 5.1 当前表到目标数据集的主要映射

| 当前对象 | 目标去向 |
|---|---|
| `instruments` | `security_master` |
| `name_history` | `security_name_history` |
| `tushare_daily` 的 OHLCVA 与前收 | `bar_daily`；原组合表降为原始/迁移证据 |
| `tushare_daily` 的估值与换手字段 | `valuation_daily` |
| `tushare_daily.factor`、`adj_factors` | 统一到 `adjustment_factor_daily`，保留价格/股本因子语义 |
| `tushare_daily` 的股本字段、`share_capital` | `share_capital_history`，明确生效日期口径 |
| `minute_bars` 及外部分钟源 | 先保留各自原始层，选定真值发布到 `bar_minute_1m` |
| Redis quote snapshot | `quote_realtime_latest` 逻辑数据集 |
| `price_limits_daily` | `price_limit_daily` |
| `stock_st_daily`、`suspend_daily`、`delisting_pool` | 规范输入经明确口径形成 `security_status_daily`；原始事件仍保留 |
| `daily_flags` | `market_flags_daily` |
| `market_regime` | `market_regime_daily` |

映射不代表简单重命名。股本、ST、停牌、退市整理等有效期语义必须在实施前逐列确认；无法确认时保留
旧表并将新数据集标为灰色“证据不足”。

## 六、历史与实时边界

### 6.1 日线

盘中“日线”是未完成聚合，不是历史事实：

1. tick 更新 `quote_realtime_latest`；
2. 实时服务从当日状态生成 `bar_daily_realtime`；
3. 历史接口只读 `bar_daily`，不会自动叠加当日盘中值；
4. 实时接口显式读取当日状态，并返回行情时间与是否定稿；
5. 收盘后执行 OHLC、量额、覆盖、交易日和来源对账；
6. 通过后原子写入 `bar_daily`，失败则保留实时证据并阻断发布。

### 6.2 分钟线

1. 当前分钟在实时状态中持续变化；
2. 已完成分钟可以进入当日临时分区，但仍标记为未定稿；
3. 收盘后检查预期时刻、根数、重复键、OHLC、成交量额和日线汇总一致性；
4. 通过后将当日分区原子发布到 `bar_minute_1m`；
5. 回测只读定稿分区；实时策略只通过带 `as_of` 的接口访问可见分钟。

## 七、表契约与关系契约

### 7.1 Dataset

每个逻辑数据集登记：

- `id`、中文名称和用途；
- 所属层与业务角色；
- 粒度、主键、时间列、分区键和排序键；
- Schema 版本与兼容策略；
- 构建入口、更新方式、定稿时点和生命周期；
- 来源、消费方、健康策略和状态；
- 是否物理落盘，或仅为实时/组合逻辑视图。

### 7.2 DatasetDependency

每条跨表依赖登记：

- 上游与下游；
- 透传、Join、聚合、窗口或发布关系；
- Join 键与预期 `1:1 / 1:N / N:1` 基数；
- 必需依赖或可选补充；
- 允许的时间延迟；
- 由该关系生成的指标；
- 关系健康策略。

边的存在由字段血缘反向推导并守护；Join 键、基数和必需性无法安全推断，必须显式登记。

## 八、健康模型

每张规范表展示总体角标和五个独立维度：

1. **时效性**：应到日期、最后数据日期、最近构建/检查时间、上下游刷新顺序；
2. **覆盖与完整性**：交易日覆盖、标的覆盖、键空间覆盖、空值和缺口；
3. **结构完整性**：Schema、字段类型、主键、唯一性、粒度和分区；
4. **真实性与有效性**：外部对账、量纲恒等式、公式重算、已知缺陷和人工证据；
5. **血缘一致性**：Join 基数、匹配率、孤儿行、日期同步和下游重建。

### 8.1 四态门禁

- `GREEN 健康`：所有必需维度都有未过期证据并通过，无未关闭问题；
- `YELLOW 有风险`：证据完整，但存在警告、已知缺陷或非阻断覆盖问题；
- `RED 不可用`：存在阻断失败；
- `GRAY 未知`：必需检查未运行、证据过期或缺少基线。

聚合顺序：阻断失败先判红；否则缺少必需证据判灰；否则存在警告判黄；全部通过才判绿。
不计算综合平均分，因为真实性失败不能被高覆盖率抵消。

### 8.2 DatasetHealthPolicy

不同表不能共用一个覆盖分母：

- 稠密日表按交易日、预期标的和 `symbol × dt` 键空间检查；
- 稀疏事件表检查采集成功、时间跨度和事件契约，合法 0 行不失败；
- 区间表检查重叠、断档和有效期；
- 冻结表检查 Schema、校验和和不可变性，不要求持续更新；
- 实时表检查行情年龄、序列连续性和服务可用性；
- 运行日志按服务节奏检查，不套用行情覆盖率。

没有明确策略的表保持灰色，不猜测阈值。

## 九、字段、表和关系三层质检

### 9.1 字段质检

沿用现有 `Metric` 与 `Check`：单位、空值、真值对账、派生重算、PIT 有效性和人工证据。

### 9.2 表质检

- 实际 Schema 与契约一致；
- 主键非空且唯一；
- 行粒度符合声明；
- 分区完整、可读且没有混入其他日期；
- 数据在允许时效内到达；
- 字段级阻断、警告和未知数量正确汇总。

### 9.3 关系质检

- 实际 Join 基数符合声明；
- 必需上游的匹配率与孤儿行符合策略；
- 上下游交易日覆盖一致；
- 上游发布后下游已经刷新；
- 派生结果可从声明上游独立重算；
- 可选依赖缺失时遵守登记的 null 语义。

页面分别显示字段状态、表契约状态和关系状态，不用一个绿色标签掩盖连接异常。

## 十、表合并与拆分建议

系统只输出证据化建议，不自动变更 Schema。

### 10.1 建议合并

只有以下条件全部满足才能给出：

- 相同粒度和主键；
- 经关系质检确认完整一对一；
- 更新节奏、生命周期、状态和恢复方式一致；
- 总是由同一生产阶段发布；
- 没有独立到货或独立消费语义；
- 相关表与关系均为绿色。

### 10.2 建议保持独立

任一情况成立即倾向保持独立：来源或到货时点不同、可选连接、一对多、被多个下游复用、
独立消费者、不同生命周期、不同定稿时点或不同失败恢复方式。

### 10.3 建议拆分评估

同表混合多个粒度、有效期、更新节奏、事实与参数化因子，或字段存在明确独立来源、生命周期和
消费边界时提示拆分。

若主键、关系或消费信息缺失，结论必须是“证据不足”。

## 十一、存储与查询性能原则

- `bar_daily` 按年分区，分区内按 `(symbol, dt)` 排序；
- `bar_minute_1m` 按交易日分区，分区内按 `(symbol, ts)` 排序；
- 不按单只股票生成大量小文件；
- 原始层按来源、批次和日期组织；
- 每个发布分区带 Manifest：Schema 版本、行数、时间范围、标的数、来源、校验和、发布时间；
- 查询必须限制日期并投影列，禁止生产代码无边界读取宽表；
- 常用跨域组合优先做逻辑视图，只有经过基准测试确认昂贵且稳定的查询才物化；
- 为日线区间、单日分钟和单标的分钟查询建立回归基线；
- 大表迁移前后使用 `EXPLAIN`、扫描文件数、扫描列数、峰值内存和耗时验收，而不是凭感觉改分区。

## 十二、页面信息架构

数据管理子导航调整为：`数据表`、`指标`、`数据源`、`验证规则`，默认进入数据表。

数据表列表显示：

- 名称、用途、所属层、业务角色；
- 粒度、主键、字段构成；
- 覆盖区间与适用的覆盖比例；
- 根来源、直接上下游；
- 最近更新；
- 红黄绿灰健康角标。

数据表详情显示：

- 表契约；
- 五维健康诊断；
- 可点击的上下游关系图；
- 字段、来源、公式和消费方；
- 表规则、字段规则、关系规则和失败样本；
- 合并/拆分建议与依据。

规则详情显示规则定义、判定条件、局限、覆盖资产、实现位置、最近结果和历史。关系详情显示 Join 键、
基数、覆盖率、孤儿行、日期差异、更新时间差和依赖字段。

颜色必须配合文字与图标，不能让颜色成为唯一信息载体。

## 十三、演进与发布纪律

新增业务表必须先完成契约、查询场景和健康策略评审，不能继续“接口来了就建业务表”。

Schema 或物理表变更遵循：

1. 新旧契约并行；
2. 回填新表；
3. 逐键、逐字段和聚合对账；
4. 影子读取并比较策略输入；
5. 查询门面切换；
6. 旧表降级为冻结审计表；
7. 无消费者且完成归档确认后才允许删除。

生产消费者不得绕过查询层直接读取原始来源路径。任何自动回退、混源或填充值都必须是显式契约，
不得隐藏在查询实现中。

## 十四、已确认决策

| 事项 | 决策 |
|---|---|
| 首版核心任务 | 从一张表看懂用途、来源、上下游和可信度 |
| 原始来源表展示 | 默认折叠到审计入口 |
| 人工验证能力 | 首版只读、可追溯，不在线改规则 |
| 健康汇总 | 红黄绿灰四态门禁，不做平均分 |
| 结构优化 | 给证据化建议，由人最终决定 |
| 使用统计 | 首版不采集查询访问埋点 |
| 实时与历史 | 物理隔离，显式查询组合，收盘质检后发布 |
| 技术栈 | 继续使用 FastAPI、Jinja、Registry、Parquet、DuckDB 和 Redis |
| 迁移方式 | 并行构建、影子验证、逐消费者切换，禁止大爆炸迁移 |

## 十五、主要风险

- 把目标表简单理解为重命名，未处理有效期、来源选择和定稿语义；
- 用统一覆盖率误判事件表、冻结表或实时表；
- 为减少 Join 再造一张长期宽表；
- 物理迁移完成前切换消费者，导致策略输入变化无法归因；
- 只验证行数，不验证键集合、字段值、PIT 和策略结果；
- 旧表仍被隐式读取，形成两套生产真值；
- 分区过细形成大量小文件，或分区过粗导致分钟查询扫描失控。

以上风险都必须在实施计划的阶段门禁中被显式拦截。
