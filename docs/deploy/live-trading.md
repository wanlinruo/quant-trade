# 小资金实盘上线手册

当前闭环为：Linux 策略核心 → Redis Streams → Windows 执行代理 → miniQMT。
首期仅启用现有 09:30 竞价后路径，专用账户总资产不超过 10 万元，配置默认只
启用 1 万元策略资金。旧 `qmt-bridge` 只能保留为影子比较器，必须使用不同的
Stream 名称，且不得连接该实盘账户发单。

## 上线前的外部事项

代码不能代办以下事项，未完成不得进入 live：券商量化权限与 miniQMT 实盘
权限开通、交易接口协议/风险揭示签署、程序化交易报告或报备要求确认、专用
账户与佣金/最低佣金/印花税/过户费核对、云主机 IP 白名单与时间同步。监管和
券商规则会变化，正式启用前以券商当日书面要求为准。

## 三道写保护

真实委托同时要求：`mode = "live"`、`orders_enabled = true`、资金账号出现在
`protected_account_ids`。示例配置永久保持 disabled。公网 Redis 必须 TLS、强
密码，并用安全组只放行两台主机；监控页面只绑定 `127.0.0.1` 或私网地址。

紧急停止：

```bash
uv run python scripts/kill.py stop "manual stop"   # 实盘核心与影子核心一起停
uv run python scripts/kill.py status               # 两个都报
uv run python scripts/kill.py resume live          # 恢复必须指名
```

该命令让核心停止开仓，通知 Windows 撤销活动委托，并落下远端/本地停止闸；
减仓单在风控层仍被允许。恢复前必须先对账，再显式执行 `resume`。系统不会
自动清仓，避免在行情或网络异常时失控卖出。

**实盘核心与影子核心是两套开关**：`control:kill` / `var/KILL` 对实盘，
`shadow:control:kill` / `var/SHADOW_KILL` 对影子。所以这个脚本的三条命令是这样定的：

- `stop` 默认**两个都停**——紧急时要的是全停，停掉没在跑的那个也无害，
  漏停正在跑的那个才要命。要单停就在原因后面加 `live` 或 `shadow`。
- `status` **两个都报**——2026-09-27 之前它只看实盘那套，观察期里明明跑着影子核心，
  它却回一句"运行中"，报的是停用中的实盘核心。查了却查错对象，比没查更危险。
- `resume` **必须指名**，不接受默认值：解除停机是危险方向。

停机标记落地的顺序也要紧：**先写本地文件，再写 Redis**。反过来的话，Redis 不可达时
`set_key` 会抛，本地标记就永远写不下去——而核心连续故障熔断时，坏的往往正是 Redis
（2026-09-27 故障演练发现，见 `docs/reference/fault-drills.md`）。相应地，
Redis 读不到时按**停机**处理：宁可误停，不可停不下来。

这条规则有个副作用要知道：Redis 持续断线超过 3 个 tick，核心熔断会真的落下本地
停机标记，Redis 恢复后它**不会自动消失**，得人工 `resume`。这是有意的——熔断之后
本就该有人来看一眼。

## 首次接入顺序

1. Windows 先以只读方式校验字段：

   ```powershell
   uv run python scripts/win_smoke_reports.py --account <账号> --qmt <userdata路径>
   ```

2. 真实执行配置保持 `mode="disabled"`、`orders_enabled=false`。用现有
   `scripts/run_paper.py` 跑 qsys 影子盘，并让旧 `qmt-bridge` 只记录比较结果、
   不连接实盘发单 Stream，连续跑满至少五个交易日；核对选股、委托意图、
   行情时间戳、费用和每日对账。
3. 仿真或券商测试环境执行部分成交、撤单、废单、Redis 断线、Linux/Windows
   重启、重复消息、心跳超时和本地 kill 文件演练。
4. 切到 live 前运行只读盘前门禁：

   ```bash
   uv run python scripts/live_preflight.py --config config/deploy.local.toml --require-live
   ```

   该门禁不仅检查 Linux 本地三道写保护，还要求 Windows 执行代理通过心跳声明
   `trading_mode=live`、`orders_enabled=true`、当前资金账号已在白名单且本地停机闸
   未生效。任一字段缺失都失败关闭，避免双端配置不一致时出现假绿灯。

5. **打开三道写保护后，先做一笔验证单**，不要等策略信号（见下节）。验证单固定
   `511380.SH × 100 份`，必须在 10 分钟 commissioning lease 内完成买入和平仓。
6. 第一阶段启用资金 10,000 元，人工盯盘；稳定至少五个交易日后才评估扩容。
   不因短期收益跳过观察期。每日收盘核对券商资金、持仓、委托、成交和报告。

## 上线验证单（先打通管道，再等信号）

**为什么不等策略自然出手**：影子盘从不下单（历史委托数 0），所以观察期再长也
证明不了下单链路——它验的是策略稳定性，不是管道。而策略约**每 3.6 个交易日**才
出手一次（2025-01 至 2026-09 实测：418 个交易日里 112 天出手）。等自然信号来验
管道，平均要等 4 个交易日，信号没来只能干等，真出了问题还分不清是管道还是策略。

所以照交易系统上线的通行做法，用一笔最小单把 QMT 那一段当场验通。故障演练已经
验过核心侧对部分成交/撤单/废单/重复回报的处理（`docs/reference/fault-drills.md`），
**唯独 QMT 适配器这一段只有真单能验**。

### 对账口径（2026-10-06，#134）

对账比两样东西：持仓和现金。两侧口径必须一致，否则红灯会因为正当操作长亮。

- **国债逆回购（131xxx / 204xxx）算现金等价物**，不进持仓比对——两侧都过滤，
  本地账本也一样（`LiveStore.initialize` 会按券商快照建本地持仓，逆回购就在里面）。
- **它占用的资金计回可比现金**：可比现金 = 券商现金 + 现金等价物的**直取市值**。
  市值一律取券商快照的 `market_value`；**取不到就判不了**，`cash_diff` 记 null，
  不按 0、也不按 `qty × avg_cost` 反推（生产实测反推值 20 万、直取值 10 万，
  反推本身就是错的）。起始资金遇到这种情况直接失败，先去修代理上报。
- **有量却报市值 0，默认算没取到，除非账户层能佐证**。判据是「逐笔市值之和 ==
  券商账户层直取的 `market_value`，且后者为正」——吻合说明逐笔读数完整，其中的 0
  是券商自己的账。2026-10-06 生产实测：`131801.SZ` 报 10 万、`131990.SZ` 报 0，
  之和正好等于账户层的 10 万，而账户总共只入金 10 万（按面值算两笔会是 20 万），
  所以那个 0 是已结算残留行的真实市值。两个 0 相等不算佐证，是没有证据。
- **影子模式下现金差只记录、不参与判定**：那个账户维护者自己还在用，转账、
  买逆回购、到期回款、利息入账都是正当的，而影子核心一张单都发不出去。
  持仓仍然必须对得上。
- **实盘模式相反**：核心是账户唯一写入方，现金差必须参与判定，不一致即停机。
- **影子的持仓差不在豁免之内**：`ShadowBroker.poll_fills` 恒为空、`on_market_data`
  不撮合，影子盘永远不会有自己的成交，所以它的持仓差只可能来自「账户里出现了核心
  不知道的持仓」——照旧阻断。
- 台账 `live_recon` 记 `mode`（shadow / live），质检 `B4.arrival` 据此分级：
  实盘不一致是阻断违规，影子漂移不是。2026-10-06 之前的行没有 `mode`，
  按「判不了」处理，不冒充任何一种。

### 开实盘前必须先定的两件对账相关的事（#134 自审，2026-10-06）

1. **逆回购利息会让实盘停机。** 可比现金 = 券商现金 + 现金等价物市值；逆回购到期时
   本金**加利息**一起回到现金，而本地账本不变，`cash_diff` 就等于那笔利息——10 万
   7 天约 29 元，远超 `cash_tolerance=10.0`。实盘模式下这会触发 kill switch。
   所以要么实盘期间账户不持有逆回购，要么给出显式的利息容差口径。**不要靠调大
   容差蒙过去**：那会同时放过真实的资金异常。
2. **旧 `live_state` 里可能躺着逆回购。** `initialize` 只在状态不存在时才跑，
   2026-10-06 之前建立的本地账本会把 `131xxx` 当策略持仓、现金也不含那笔钱。
   升级后两侧都会把它从持仓比对里过滤掉，但本地现金仍然少了一整笔，实盘模式下
   开机即停机（这是**响的**失败，不是静默的）。启用写保护前先核对
   `live_positions` 里有没有现金等价物；有就按部署步骤重建基准。
   当前生产影子盘的账本里没有（`live_equity` 市值恒为 0），所以这条是预防性的。

### 验证标的：511380.SH × 100 份

原计划的 `510300.SH` 是股票 ETF，按上交所规则实行 T+1，当日买入不能当日卖出，
不适合验证“买入 → 持仓 → 卖出 → 空仓”的日内闭环。2026-10-09 改为
`511380.SH`（博时可转债 ETF）：

- 上交所产品资料确认其为债券型 ETF；债券 ETF 支持 T+0 当日回转；
- 最小买入单位 100 份；2026-10-09 收盘约 12.8 元，单次名义金额约 1,280 元；
- 验证工具固定代码、数量和 3,000 元上限，不接受其他标的或更大数量；
- 只用实时 QMT 买一/卖一选择限价，价格档位 0.001 元，偏离保护带 0.5%；
- 债券 ETF 不套用 A 股印花税/过户费模型。工具以成交前后券商现金快照变化反推本次
  实收费用，并与券商客户端人工核对；首笔策略股票成交后再完成股票费率模型验收。

参考：[上交所 511380 产品资料](https://www.sse.com.cn/disclosure/fund/announcement/c/new/2026-06-26/511380_20260626_CZVM.pdf)、
[上交所 ETF T+0 说明](https://www.sse.com.cn/assortment/fund/etf/question/c/c_20240118_5734755.shtml)。

### 为什么需要 10 分钟验证窗口

实盘 agent 在 core 心跳消失后会独立撤单并落下 Windows 本地停机闸；但验证单又必须
停 core，避免本地账本不知道人工持仓而触发对账停机。不能靠伪造 core 心跳绕过。

`scripts/commissioning_lease.py` 提供一个最多 10 分钟、Redis 可审计的例外窗口：

- 只允许交易日 `09:35–11:15` 或 `13:05–14:40` 武装；
- 武装前强制检查账户空仓、市场/账户/agent 快照新鲜、core 已停、kill 未生效；
- 窗口内 agent 拒绝所有普通策略订单；买入只接受 `511380.SH × 100` 限价单，
  卖出只接受不超过 100 份且与账户实际可用残仓精确相等的平仓单；
- 窗口过期而 core 仍无心跳时，agent 恢复原有失败关闭：撤单并落本地停机闸；
- 买卖完成并确认空仓后，必须先启动 live core（或把双端退回 shadow），再解除窗口。

### 核心必须先停

`LiveRuntime` 启动时拿本地推演的持仓与券商快照对账，一笔它不知道的手工持仓会直接
判不一致并触发停机。所以顺序是：

1. `systemctl stop qsys-live-core`（代理与行情网关保持运行）
2. 在 agent 仍为 shadow 时武装 10 分钟验证窗口，再把 Linux / Windows 三道写保护打开
3. 确认 agent 心跳声明 `commissioning_lease_active=true`，且
   `live_preflight --require-live` 全过
4. 读取 `511380.SH` 实时 QMT 买一/卖一；以实时卖一作为买入限价执行 100 份
5. 确认完整成交、券商持仓 100 份且 `available_qty=100`；若只部分成交，先确认撤单终态，
   再按账户快照中的实际可用残仓数量走恢复卖出，禁止补买或重复买入
6. 以实时买一作为卖出限价平掉实际可用持仓（正常路径为 100 份），确认账户回到空仓
7. 与券商端逐项核对：券商委托号、`order_remark`、成交号、成交价、实收费用
8. 启动 `qsys-live-core`，等 core 心跳和首次对账通过后解除验证窗口

```bash
uv run python scripts/commissioning_lease.py arm \
    --config config/deploy.local.toml --confirm ARM_511380.SH
uv run python scripts/commissioning_quote.py --config config/deploy.local.toml
uv run python scripts/commissioning_order.py --symbol 511380.SH --side buy \
    --qty 100 --limit <实时卖一> --confirm 511380.SH \
    --record /data/qsys/var-deployments/commissioning.jsonl
```

买入完整成交且账户快照明确显示 100 份可用后，重新读取行情，再执行卖出：

```bash
uv run python scripts/commissioning_quote.py --config config/deploy.local.toml
uv run python scripts/commissioning_order.py --symbol 511380.SH --side sell \
    --qty 100 --limit <实时买一> --confirm 511380.SH \
    --record /data/qsys/var-deployments/commissioning.jsonl
```

若买单只成交了 `N` 份，脚本会先全撤并返回失败。必须先在券商端确认原委托已终态、
账户快照显示 `total_qty=available_qty=N`，然后把卖出命令的 `--qty` 改成 `N`；工具与
agent 都会拒绝数量不等于实际残仓的卖单。不得为了凑整手再补买。

脚本自带护栏，任一条不满足直接拒绝、不发单：三道写保护全开、验证 lease 有效、
固定标的、买入固定 100 份（恢复卖出可为实际残仓）、金额 ≤ 3000 元、
市场/账户/agent 快照新鲜、实时盘口有效、
停机开关未生效、**实盘核心未在运行**、买前空仓、卖出数量与目标实际可用持仓精确一致。
只接受限价单。30 秒未完整成交会自动发送 `cancel_all`，并把部分成交/撤单状态写入
JSONL；没有确认完整成交时返回失败，禁止把部分成交当成功或直接重复下单。

成交后必须等券商账户快照同步：正常买入后明确出现 100 份可用持仓，卖出后明确归零。
工具用成交前后现金变化与成交额反推实收费用，并将模型费用单独命名，不能把两者混为
一谈。首笔策略股票成交时再核实“不免五”、印花税与过户费，**不要反过来改模型去
迁就未知口径**。

标的选流动性好、成交确定性高的，不要选当日候选股——验证单是验管道，
不该和策略持仓搅在一起。

## 进程与恢复顺序

启动顺序：Redis → miniQMT → Windows agent → market gateway → 盘前检查 → live
core。停止顺序反过来，先执行 kill/cancel。Linux unit 模板位于
`deploy/systemd/qsys-live-core.service`；复制后要按实际用户和路径修改。行情网关
依赖 QMT，也和 agent 一样运行在 Windows。Windows 使用任务计划程序或 NSSM
分别守护 `scripts/run_agent.py` 与 `scripts/run_market_gateway.py`，设置“无论用户
是否登录都运行”、失败一分钟后重启；账户级 lock 文件不可共用。

成交回报在组合状态和成交明细同一 SQLite 事务落盘后才 ACK；核心重启会恢复
未终态委托，Windows 重启则通过券商 `order_remark` 找回原委托并避免重复下单。
`var/live-state.sqlite3`、`var/agent-ledger.sqlite3` 和 warehouse 每日加密备份，
备份恢复演练至少每季度一次。

## 盘中门限

- 单票不超过账户净值 5%，总敞口不超过 10%，启用资金 10,000 元；
- 单笔不超过 10,000 元，日换手不超过日初净值 100%；
- 日内亏损达到 2%、连续拒单达到 3 次、核心/代理心跳超时或策略事件超过
  30 秒 SLA，即停止开仓并撤单；核心存活心跳独立于同步事件执行，不能用新鲜心跳
  掩盖事件卡死；
- 买单不超过当时累计成交量 5%，且不超过前一交易日成交额 1%；
- 委托价格相对买一/卖一偏离不超过 2%，停牌、涨跌停和 T+1 由共用约束拦截。

每个交易日结束发送净值、成交、拒单和 EOD 对账报告。任何对账不一致、无行情、
账户快照超过 5 秒、心跳超过 10 秒，都视为不具备自动开仓条件。
