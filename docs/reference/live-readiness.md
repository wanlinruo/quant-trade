## 策略承袭链

**回测 → 模拟账户 → 影子/实盘核心**。两个运行模式不再各自填参数，而是按
部署配置 `[strategy] follows_paper_account` 指向的模拟账户，读它存档的策略源码与参数：

```toml
[strategy]
follows_paper_account = "29056f15bfff415b"
workbench = "var/workbench/workbench.sqlite3"
```

源码快照写进当前运行 workspace 的 `strategy.py`，账户取不到就拒绝启动，不退回默认参数。
这样从模拟、影子到实盘的策略口径不会漂移。当前 live core 承袭：模拟账户
`29056f15bfff415b`（2026-09-24 生效，09:25:10 / 3% / 0.5% / 连续竞价判定）。

页面上的体现：
- **影子盘（`/live`）**：「策略与来源」列出承袭的模拟账户（可点进去）、其来源回测、
  策略源码版本与参数；「影子盘 vs 模拟交易」按累计收益率逐交易日对比，只取两边都有
  记录的交易日。
- **模拟交易详情**：历史曲线在策略与沪深300之外加一条影子盘曲线，**仅当影子盘承袭的
  正是这个账户**；本金不同故统一比收益率，影子盘以本账户首个交易日为基准。

## 影子盘的观察期数据缺了两天（2026-09-30 核对）

| 交易日 | 模拟盘 | 影子盘 |
|---|---|---|
| 09-24 | 7/7 | 7/7 |
| 09-28 | 7/7 | **3/7** |
| 09-29 | 7/7 | **1/7** |

影子盘那两天是逆回购对账停机造成的（09-28 15:30 停、09-29 15:07 恢复），
不是策略或数据问题——同一天模拟盘跑得完好，三套引擎在 09-28、09-29 的竞价决策
结论也一致。

**判定口径：以模拟盘为准，10-09 满期**（2026-09-30 维护者决定）。理由：

- 观察期验的是**策略能不能每天无错跑完**，而模拟盘承载的是同一套策略与参数
  （影子盘正是承袭模拟账户 `29056f15bfff415b` 的源码与参数）；
- 影子盘**本就不下单**，它证明不了下单链路——那部分由 10-09 的上线验证单来验；
- 缺的那两天，三套引擎的竞价决策结论完全一致，说明策略侧没有分歧，
  缺的只是影子盘的事件记录。

若当初要求两条链都连续 5 天干净，影子盘需从 09-30 重算、顺延到 10-14。

### 停机还留下一个更隐蔽的后果：选股用了过期的 T-1

2026-09-30 影子盘候选 27 只，模拟盘 44 只——同一天同一套策略不该差这么多。
查下来影子盘的 `previous_session` 停在 **09-28**，模拟盘是 09-29。
对照首板数（09-28 有 28 只、09-29 有 46 只）正好对上。

成因：09-29 影子盘停机，`session_start` 只完成日初结算、策略没跑，
`last_session` 没推进到 09-29；今天读出来的就还是 09-28。**它拿前天的首板
在选次日票，而且不报错、不告警。**

这在实盘上是真问题：任何一天核心没跑完，第二天就会静默地在错误的股票池上交易。
今天恰好被候选数差异暴露，若两天首板数接近则谁都看不出来。

**已修**：攒的值要和交易日历对一次——一致就照常用攒的（口径不变），
不一致说明漏了交易日，以日历为准并记 `strategy.stale_previous_session` 告警；
日历答不上来时仍然用攒的（新账户第一天正是靠它）。

影子盘的状态会在 10-08 自愈（今天 `session_start` 已正常跑完，
`last_session` 推进到 09-30，与日历一致），不需要手工改状态库。

### 顺带查清的两件事

**账户数据本身没坏**：影子盘现金 50,000、空仓、权益曲线自 09-18 起一直平直，
与它从未下过单相符。

**风控基准跟着券商账户走**（`runtime.py` 日初结算处取 `remote.total_asset`）。
这对实盘是对的——实盘就是那个账户；但它意味着**逆回购锁住的钱也会被算进
仓位上限的分母**。维护者已确认 10-08 到期后不再续作，届时自然消除；
若将来再做逆回购，开实盘前要重新评估这一条。

## 时刻轴上那几块红，哪些是真的

「每日业务验收」上 2026-09-21 起有三块红，性质不同，别一起看：

| 日期 | 时刻轴显示 | 实际 | 判定 |
|---|---|---|---|
| 09-21 | 事件失败 | `auction:09:30:00 事件已过期，未补跑` | **真故障**：09:30:06 行情请求超时、30 秒宽限期内没能重试。已修（超时 5→20 秒、宽限 30→120 秒） |
| 09-24 | 事件失败 | 7 个事件全部 completed、无 error，竞价 09:25:10 跑出「候选 34 只 → 通过 0 只」 | **误报** |
| 09-28 | 事件失败（上午） | 同上，竞价 09:25:10 跑出「候选 36 只 → 入档 1 只 → 闸门通过 0 只」 | **误报**，10:18 修复后转正常 |

误报的成因：新账户把竞价决策改到 09:25:10（参数 `auction_at`），而实时健康采样器
里的预期时刻还写死 09:30。**从 09-24 新参数上线那天起就一直红着**，直到 09-28
维护者在页面上发现才查出来——我此前几次巡检都只看了 `systemctl --failed`
与当晚质检，两者都不预设时刻，所以都是绿的，反而掩盖了它。

修复见 PR #77（预期时刻改为逐账户读 `auction_at`）。
**历史观测没有改写**——监控记录是审计凭据，宁可留着红块加一段说明，
也不回头粉饰。所以 09-21 与 09-24 的红会一直留在时刻轴上。
