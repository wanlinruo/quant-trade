# 数据目录请求延迟（#442）

## 2026-10-20 现场定位

当前生产 Web `dfd65bf`、共享 checkout `ee7b0a3`。目录与分钟详情连续请求约 30 秒，
首次客户端 20 秒超时；healthz、实盘与服务详情正常。源码与 installed coverage.py 哈希一致，
不能用“只发生一次冷缓存”解释。

以实际 `qsys-web` 账号/venv、生产只读输入分段测量：

- 文件发现、resolve/stat 共 0.332 秒；DataAssetService 初始化 0.011 秒。
- 在 CPUQuota=50%、MemoryMax=1 GiB、Nice/IO idle、240 秒上限下，连续两次表目录调用
  为 66.287 / 62.573 秒，原缓存分别 miss=1 / miss=2。
- 其中 `bar_minute_1m` 1,939,040,036 行，单次精确聚合 49.981 / 49.892 秒；
  数据库另限定 256 MiB 内存、512 MiB spill、单线程。
- 单独间隔 3 秒的文件身份快照，仅 `live_equity/year=2026/part.parquet` 变化。
- 健康证据单独测量 7.218 秒（CPUQuota=25%，含首次依赖加载），后续单表查询通常为毫秒级。

隔离探针的资源配额与生产 Web 不同，上述 wall time 不直接当作同条件 HTTP 对比。

`health-profile-before.log`。探针未读取完整配置，未写 warehouse 或交易状态。

## 根因与修复

原缓存以整个 warehouse 的文件快照为单一键。权益表持续原子替换，即使所有行情历史不变，
也会使全仓库缓存失效，重复扫描约 19 亿行分钟数据。

修复按数据集缓存精确结果，文件路径、设备/inode、大小、mtime/ctime 与仓库身份共同限定
复用范围。缓存有容量上限；原子替换、分区增删会失效。查询期间文件变化时不把结果登记为
匹配旧文件身份的当前缓存。没有从名称、价格、档位或其他来源推断数据。

生产表目录/详情首次统计在单一后台线程执行，HTTP 请求只做文件发现、缓存读取与原有健康
证据查询。未完成显示“统计中”，失败显示“统计暂不可用”。更新期间若有上次真实结果，
必须同时标明统计时间与“更新中/更新暂不可用”；不将旧值冒充当前值，不填零、不用近似统计。
读取失败设重试间隔，避免每次页面请求重复触发失败作业。

浏览器仅更新统计单元格，不整页重载、不打断阅读。统计完成不会把灰色质量证据改绿；
原有红黄灰和 TTL 判定保持原语义。阻塞式 `coverage()` 继续供 CLI 等既有消费者使用。
