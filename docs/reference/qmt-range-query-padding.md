# QMT 区间查询会填充未成交的分钟（2026-10-04）

脚本：`scripts/win_download_minutes.py`、`win_download_daily.py`、
`win_download_auction_ticks.py`。

**一句话**：`xtdata.get_market_data` 按**区间**取数时，会把当日首笔成交之前的空白
分钟用**昨收价**填满、`volume=0`；按**单日**取则不会。同一接口、同一标的、同一天，
两种调法给出不同的东西。

## 1. 怎么发现的

做 T+0 ETF 选品时探 QMT，发现 `513100.SH` 国泰纳斯达克100ETF 的分钟线稳定只有
180 根，而同期其他 ETF 和个股都是 241 根，7/7 个交易日复现。

查下来 180 根是**对的**：该标的当日首笔成交在 10:31，09:30–10:30 共 61 分钟确实
无成交，241 − 61 = 180。三条独立证据：

- 返回的 180 根**没有一个 NaN**，不是"有行无值"
- QMT 180 根的 `volume` 合计 1,355,323 **等于** Tushare 日线 `vol` 1,355,322.68
- QMT 首根 `open` **等于** Tushare 日线 `open`（2.291）

真正的问题在后面：同一天用 `--whole-window` 整窗下载再导出，parquet 里变成了 **241 行**，
多出来的 61 行是这样的：

```
09:30  open=high=low=close=2.304  volume=0  amount=0
09:31  open=high=low=close=2.304  volume=0  amount=0
...  一直到 10:30，61 根完全一样
```

`2.304` 是该标的的**前收盘价**（Tushare `pre_close` 正是 2.304）。

## 2. 根因

`get_market_data` 的 `start_time`/`end_time` 跨多日时，返回的是一张**按交易日×241 分钟
对齐的网格**，当日首笔成交之前的格子用昨收价补齐、成交量置 0。单日查询（`start_time`
与 `end_time` 同为一天）返回的则是从首笔成交开始的真实序列。

**按股-日下载并不能避开它。** `win_download_minutes.py` 默认按股-日调
`download_history_data`（为省 QMT 缓存磁盘），但读回时是：

```python
data = xtdata.get_market_data(
    field_list=[], stock_list=[symbol], period="1m",
    start_time=min(stamps), end_time=max(stamps),   # ← 区间，于是被填充
    dividend_type="none",
)
```

下载方式和读取方式是两件事，省磁盘的那个选择没有改变读取口径。

## 3. 污染程度（2026-10-04 实测）

| | ETF 研究批 | 生产 `minute_bars` |
|---|---:|---:|
| 总行数 | 10,834,576 | 233,673,841 |
| 整日虚构 | 716,734 行（6.62%）/ 2,974 标的日 | 10,122 行 / **42 标的日** |
| 前导填充 | 651,319 行（6.01%）/ 13,001 标的日 | 10,716 行 / 9,972 标的日 |
| **合计虚构** | **1,368,053 行（12.63%）** | **20,838 行（0.01%）** |

生产批干净得多，因为首板候选都是活跃票、09:30 就有成交；ETF 批重，是因为池子里有
大量流动性差的和窗口内才上市的标的（上市前整天被填满）。

生产的前导填充长度分布——**95% 只有 09:30 那一根**：

| 填充根数 | 标的日 |
|---:|---:|
| 1 | 9,506 |
| 2 | 322 |
| 3 | 78 |
| 4–8 | 65 |
| 15 | 1 |

09:30 是集合竞价那根。生产里还有 **42 个标的日是整天虚构的**：241 根全是昨收价、
成交量全 0，那一天在数据里存在，而市场上它根本没交易。

## 4. 为什么质检没发现

服务质检的分钟线判据是**「每只 241 根」**和**「全天成交量对日线（≤1 手）」**。

- 「241 根」不仅没发现问题，**它本身就是被填充满足的**——填充的作用恰恰是把不足
  241 根的日子补齐到 241 根。它还会把 `513100` 这类首笔成交晚的**正确**数据误报成缺失。
- 「成交量对日线」对填充**天生失明**：填充行 `volume=0`，合计永远对得上。

**这两条判据组合起来，对这个缺陷是完全盲的。** 第一次校验因此报出"188 只全干净"，
是错的。暴露问题的是"241 根"这个计数与已知事实（513100 单日查询只有 180 根）的矛盾。

**正确的判据**：每个标的日的首根必须有成交（`volume > 0`）。

## 5. 剔除规则

**删除每个标的日首笔成交（`volume > 0`）之前的所有行；该日无任何成交则整日丢弃。**

纯删除，不新增、不推算任何值，符合「只许直取或纯派生」。

ETF 研究批已于 2026-10-04 套用，四项验证：

| 验证 | 结果 |
|---|---|
| 剔除后仍有前导填充 | 0 |
| 剔除后整日无成交 | 0 |
| `513100` 2026-09-29 | 180 根、首根 10:31 —— **与单日查询一字不差** |
| 成交量合计变化 | **0** —— 删掉的确实全是 0 量根 |
| 剩余标的日 | 41,983 —— **精确等于** Tushare 日线基准的 41,983 |

最后一条是独立交叉验证：剔除后的标的日数与另一个数据源的日线记录数完全相等。

数据位置：可用数据 `/data/qsys/research/etf-minute/`；原始下载保留在
`/data/qsys/research/etf-minute-RAW-CONTAINS-PADDING/`，仅供复验，带 README 警示。

## 7. 教训

发现这个缺陷靠的不是质检，而是**一个计数和已知事实对不上**。当时已经确知
`513100` 单日查询只有 180 根，而校验报告说"全部 241 根、188 只全干净"——两者不可能
同时为真。沿着这个矛盾往下查才看到填充。

质检判据选错时，它不会报警，它会发出"一切正常"。
