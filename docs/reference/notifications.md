# 消息通知

三类消息分三路，互不干扰：

| 类型 | 触发方 | 去处 | 配置位置 |
|---|---|---|---|
| 策略 | 各模拟账户 | 该账户自己的企微机器人 | 账户详情页「企微通知」 |
| 策略 | 实盘核心 | `[alerts] webhook_url` | 节点 `config/deploy.local.toml` |
| 策略 | 影子核心 | `[alerts] shadow_webhook_url` | 同上（不填则退回 `webhook_url`） |
| 运维 | 服务质检、健康采样器 | `[alerts] ops_webhook_url` | 同上 |
| 每日汇总 | 定时任务 20:30 | 邮件 | 节点 `[email]` 段 |

**告警是旁路**：任何一个通道发送失败都不中断主流程，也不影响别的通道
（`qsys.ops.alerts` 的既有约定）。通知链路自己挂了，交易照跑。

## 策略消息：只在四种情形推

三个引擎每天各 7 个事件，全推是骚扰，几条之后人就不看了——那时真出事反而被淹掉。
判断在 `qsys.ops.notify.should_notify`：

| 情形 | 为什么值得打扰你 |
|---|---|
| 有实际买卖（下单/拒单） | 钱动了 |
| 竞价决策结果（每日 09:25） | 每天一条，即使不交易也推——这是确认策略还活着的那条消息 |
| 策略出错 | 必须知道 |
| 收盘汇总 | 当日结果 |

`bar`（15:00，只更新收盘价、不做决策）从不单独推。`session_start`（09:15）与
三次 `checkpoint`（11:25 / 14:25 / 14:50）**只在手里有票时推**。

这条线是这么划的：空仓时 `on_checkpoint` 第一行就 `return`，推一条「持仓 0 只，
无动作」是在报告一件没发生的事——历史上 **73% 的交易日是空仓的**（418 天里
112 天有交易），那就是每天三条空消息，连推两个多月才遇上一次有内容的，
人到那时已经不看了。有持仓的那几天正相反：这三个时刻是**对钱做判定的时刻**，
14:50 更是当天最后一次离场机会，「看了没卖」和「没看」必须分得出来。

于是：**空仓日每引擎 2 条，有持仓日 6 条**。

盘中那条要说清**为什么不卖**。退出规则是 FROZEN 的，`_HOLD` 不带原因，所以
`on_checkpoint` 只陈述判定用到的事实——走哪条分支、现价、相对成本、结论；
某些时刻只对特定分支生效（14:25 只管 LOW，14:50 只管 HIGH），那就直说
「本时刻规则不适用」。**上报不参与判定**，一行决策逻辑都没动。

取不到盘中价也会出现在消息里：那会让持仓卡住（603809.SH 曾因此从 2025-12-26
一直挂到区间末尾，把现金抽干、连累后面 16 笔该买的没买成），静默跳过不行。

### 「没消息＝出事了」靠什么保证

每天固定的 09:25 与 15:30 两条就是策略心跳。但更可靠的是**运维通道在主动盯**：
策略事件没按时落库，`BusinessAlertTracker` 会推「策略事件延迟 / 链路失败」。

这比靠「没收到」重要得多——**让一个已经挂掉的组件自己报告自己挂了，本身就不可靠**；
策略进程死了，它发不出任何东西，包括「我死了」。只有外部观察者说得出这句话。

### CRITICAL 两边都发

实盘对账失败、心跳超时、连续拒单熔断，**既是交易事件也是运维事故**：交易者要
知道钱出了问题，管理者要知道系统停了。这类 CRITICAL 同时进运维群
（`MinSeveritySink`），其余只进策略群——每天的竞价决策推进运维群只会把真正的
事故淹掉。两个地址相同时不重复装配，否则每条严重告警发两遍。

### 多个模拟账户共用一个群

账户名不够分：它们跑同一条策略，名字只差后缀，手机上扫过去几乎一样。消息里的
引擎名带账户 id 前六位——`StructuralStrategy-模拟#b5b2cf`——既一眼能分，
又能直接拿去工作台页面对上号。

分级：出错走 CRITICAL，有拒单走 WARNING，其余 INFO。

### 消息里要有能据以决策的东西

2026-10-01 从交易者视角重看了一遍，发现消息**只有计数**：

```
实盘｜下单 2 笔
持仓 2 只，下单 2 笔
总资产 96,294.75（现金 96,294.75，持仓 0 只）
```

手机上收到这条，不知道买了哪只、什么价、多少钱，也分不清是建仓还是离场——
**而离场才是钱回来的时刻**。现在：

```
实盘｜买入 1 只
候选 46 只 → 入档 3 只 → 闸门通过 1 只 → 下单 1 笔
　入档前·不在低开/高开价格带 43　闸门·BREADTH_OTHER 2
　买入 600036.SH 300 股 @ 41.07（12,321 元）
总资产 100,000.00（现金 87,679.00，持仓 1 只）
```

四处变化：

- **标的、方向、数量、价格、金额**逐笔列出（`TradeContext`，不入库，只用来组织消息）
- **买卖分标题**：「买入 2 只」「卖出 1 只」「买入 2 只，卖出 1 只」
- **拒单说明是哪只、为什么**，不再只给个数字
- **收盘报当日盈亏与持仓明细**。T+1 策略晚上要知道手里是什么、成本多少——
  明天开盘就要卖

收盘那条报的是**整天**，不是最后一个事件：照抄事件级摘要会写出「无下单」，
而下面正列着当日成交（预览真实消息时发现）。

当日盈亏＝今天总资产减上一个有记录交易日的总资产。**第一天不显示盈亏**，
拿初始资金凑一个数不如不说。

模拟账户此前连收盘盈亏都没有——实盘与影子有 `daily_report` 的净值与涨跌幅，
模拟账户只有「持仓 0 只，无下单」。而模拟账户恰恰是观察期里真正在看的那两个。
现在三条链同一套口径。

影子与实盘各用一个机器人：观察期两条链同跑，消息交错在一个群里分不清是谁发的。

### 重复的事只说一次

对账不一致这类**持续存在**的状况，只在结论变化时留痕与告警（坏了一次、好了一次）。
2026-09-29 之前是每次尝试都记：一个持续存在的差异写进 10,383 条对账记录
（每 2 秒一条），既撑爆仓库又让 `B4.arrival` 永远红着。告警同理——
同一句话推一整天，几条之后人就不看了，那时真出事反而被淹掉。

## 运维消息

服务质检（交易日 20:00）跑完后把结论推给运维机器人。**这一步以前完全没有**：
质检失败只写进运行记录，要人自己去翻页面——2026-09-27 的证书续期失效就是这样
躺了一天，最后是偶然翻 `systemctl --failed` 才发现的。

质检每天只跑一次，不存在刷屏，所以不做去重：连续几天不好本来就该天天提醒。

**但它必须质检今天。** 原本取「最近一个已收盘交易日」，于是假期里天天重查节前
那一天：运维群连收五条一模一样的结论，日报还把它当成当天的质检结果——
2026-10-01 国庆第一天，同一封信里「数据质量：休市日不安排验证」和一份 09-30 的
验证结论同时出现。现在休市日直接跳过（交易日 20:00 跑时两种取法等价）。

实时健康采样器（每 5 分钟）另有 `BusinessAlertTracker` 做**边沿触发**——
坏了报一次、恢复报一次，不会每 5 分钟刷屏。

它一度发错群：2026-09-29 配好三个机器人时，采样器仍用 `webhook_url`（实盘群），
不是 `ops_url`。影子链路当时没出过事，所以两周没人发现。实盘一开，这会两头吃亏
——实盘群被运维噪音淹，运维群反而漏掉事故。现在由 `ops_sinks()` 统一决定去向，
有测试守着（2026-10-01 修）。

### 基础设施实时看护

健康采样器每 5 分钟巡检一次（`--infra-interval`），发现就推运维机器人：

| 项 | 告警 | 严重 |
|---|---|---|
| 磁盘剩余 | < 20 GiB | < 10 GiB |
| 站点证书 | < 21 天 | < 10 天 |
| `systemctl --failed` | — | 任一单元失败（**逐个单元独立计数**） |
| 急停开关 | — | 已触发 |
| Redis | — | 不可达 |

以前这些**只有每晚 20:00 那一次机会**，或者根本没人看：证书续期失效躺了一整天
（2026-09-26）、fwupd 单元长期 failed 污染 `systemctl --failed`（2026-09-30），
两次都是偶然翻出来的。

另外**任何服务进程掉线**都会报一次、恢复再报一次。以前只有模拟盘与影子盘的
**业务链路**有告警，Windows 上的行情网关、执行代理整个停掉一声不响——
而这两个恰恰是实盘的必经之路。

判定与去重都是纯函数（`qsys.ops.infra_watch`），采集在调用方，所以每条阈值
与措辞都测得动。

#### 两条自律

**边沿触发**：出事报一次、恢复报一次。国庆七天 Windows 不开机应该是一条告警，
不是两千条——连续报警和不报警一样没用，因为人会开始无视它。

**问不出来就沉默**：实时通道只报确凿的坏消息。采样器自己连不上 Windows 时
刷一串「离线」比不报更糟；未知交给每晚质检和日报去说。首次采样也不报——
采样器刚起来时不该把本来就停着的东西当成刚发生的事故补报一遍。

### 投递留账

`AlertBus` 可以带一本 `AlertLedger`，把每条告警的投递结果按天追加成
`var/alerts/YYYY-MM-DD.jsonl`。

为什么需要：**通知链路自己挂了是最难发现的一类故障**。机器人 key 被撤、群解散、
出口网络被墙，全都静默——告警发不出去，而「告警发不出去」这件事本身也要靠告警
才能知道。留了账，日报每天报一句「今天推了 N 条、失败 M 条」，把静默变成数字。

留账是**旁路的旁路**：写失败只记日志，绝不反过来影响告警与主流程。

## 配置

### 模拟账户

账户详情页「企微通知」填 Webhook，留空即关闭。链接是凭据：
**存进账户配置、页面上永远只回尾部 6 位**，完整值不回显。只接受 `https://`。

### 影子盘 / 实盘 / 运维

节点本地 `config/deploy.local.toml`（已 gitignore，不入库）：

```toml
[alerts]
webhook_url     = "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=策略机器人"
ops_webhook_url = "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=运维机器人"
timeout_seconds = 5.0
```

`ops_webhook_url` 不填则退回 `webhook_url`。**建议分开**：运维消息要立刻看，
混在每日策略决策里会被淹掉。

`WebhookAlertSink` 的载荷本来就是企微机器人的 `msgtype/text` 格式，
钉钉、Server 酱等同样可用。

## 每日汇报邮件

每天 20:30 发一封（服务质检 20:00 之后——要等它的结论才写得出「今天正不正常」）。
内容组装在 `qsys.ops.digest`（纯函数，不碰数据库），取数与投递在
`scripts/send_daily_digest.py`。

**先说结论，再说明细**：标题就写「正常」或「有异常 N 项」，正文开头重复一遍需要
关注的条目，往下才是分节明细。日报如果要读完才知道有没有事，很快就没人读了。

七节：策略（各引擎当日竞价决策、出错、委托合计）、账户（当日最后一条权益）、
数据质量（指标字典当晚结论）、服务与数据（质检结论与明细、当天没留下记录的任务）、
节点（磁盘、内存、证书、失败单元、常驻服务在线状态）、通知（今日推送与投递失败）、
实盘就绪（运行模式、急停、连续零错误天数、券商代理心跳）。

### 告警也算异常

`Line` 带严重度（ok / warn / bad）：**告警计入结论**，只是排在失败后面。
标题写成「有异常 3 项（失败 1，告警 2）」。

2026-09-30 指标字典有两条阻断，每晚质检把它记成 warning，日报把它列了出来、
然后在标题上写「正常」——信号到了，被降噪降掉了。只分「有事 / 没事」不够。

### 数据质量单独成段

以前指标字典的结论只在服务质检里占一行（「26 项，失败 0，告警 2」），
上面那次就是这么被读过去的。现在单独一段，阻断项逐条点名。

### 节点段：休市日的全部意义

磁盘、内存、站点证书剩余天数、`systemctl --failed`、五个常驻服务的在线状态。
阈值与每晚质检同口径（磁盘 20/10 GiB，证书 21/10 天）。

**问不出来就写「问不出来」**，不写「看起来没事」。在 Mac 上跑、在没有 systemd 的
容器里跑、权限不够，都属于未知；把未知当健康是监控里最贵的错——2026-09-26 证书
续期失效躺了一整天，就是因为没人问、也没人发现没人问。

### 实盘就绪：只报查得到的事实

不回显手写的计划表——**过期的「一切就绪」比没有这一段更糟**。四项每天重算：
跑在什么模式、急停在不在、两条链各连续多少个交易日零错误、券商代理还有没有心跳。

「连续零错误多少天」替代了「观察期第几天」：后者需要一个手填的起点，会过期；
前者每天都能从状态库重算，而且实盘跑起来之后依然有意义。

### 休市日也发

以前不发——定时器按 `Mon..Fri` 触发、不认节假日，脚本却取「最近一个已收盘交易日」，
于是国庆七天会把 09-30 那封原样重发五遍（2026-10-01 预演证实）。

现在汇报的是**今天**。休市日照发，但不拿交易日的尺子量它：没有策略与账户段，
盘前取价、归档、同步、验证、质检也不算「未运行」。机器还在跑、磁盘还在涨、
证书还在倒计时——这些照报，真出事照样发得出来。

两处排版约束是拿真实数据跑出来才发现的：

- **多行错误压成一行**并截断到 140 字。对账不一致会逐个列出标的，原样铺开能把
  日报撑成几十行。
- **同一故障跨事件只说一次**。一次对账失败会让 checkpoint/bar/session_end 全报
  同一句，标成「（4 个事件）」即可。

实测把 45 行压到 24 行。

### 配置

```toml
[email]
host       = "smtp.qq.com"
port       = 465
username   = "你的邮箱@qq.com"
password   = "…"            # SMTP 授权码，不是邮箱登录密码
recipients = ["收件人@example.com"]
use_ssl    = true          # 465 用 SSL；587 改成 false 走 STARTTLS
```

没配 `[email]` 时任务照常跑，只打印内容并把运行记录记为「跳过」——
这样在拿到 SMTP 之前也能先看汇报内容对不对。

```bash
# 只看不发
uv run python scripts/send_daily_digest.py --day 2026-09-28 --print
```

定时任务 `qsys-daily-digest.timer`，`OnCalendar=*-*-* 20:30`——**每天**，
不是 `Mon..Fri`。它在注册表里的 `cadence="everyday"`：看板对交易日任务在休市日
显示「休市」，这条规则不能套到它身上，否则整个国庆假期一封没发也全绿。

单元里的 `--warehouse` / `--tls-site` 不是可选项：缺了「数据质量」段会在交易日
判成「当日没有验证结果」，天天误报。
它不产出数据表——价值在发出去的那封信，所以「每个定时任务都要有产出表」
这条不变量为它放宽了。
