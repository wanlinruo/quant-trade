# Live连续故障熔断（#535）

关联[Issue #535](https://github.com/wanlinruo/quant-trade/issues/535)。本修复为离线准备，
不授权启动旧Live、清KILL或生产故障演练；真实撤单/持仓与恢复仍受#541/#533门禁约束。

## 故障与行为

原入口在连续三次tick失败后先落本地KILL，再通过Redis请求撤单。如果Redis继续超时，
`cancel_all()`异常直接退出入口，后续critical告警也被跳过。10-24真实故障已记录于#535；
Redis超时的基础设施根因和券商实际撤单结果仍未知。

准备修复在本地KILL成功落下后锁定当前进程，仅尝试一次撤单请求。撤单接口抛普通异常时，
结果记录为未知，并继续提交critical告警；接口返回也只说明请求调用返回，不证明券商已撤单。
锁定后不再执行`runtime.tick()`，独立心跳线程和进程保留，避免自动重播撤单、调度策略或
因该异常退出而被systemd反复拉起。核对券商状态及故障后，恢复需要人工处理并重新启动；
重启本身不清KILL，原有姿态、快照、锁与恢复门禁继续生效。

只捕获撤单调用异常，不吞掉`BaseException`或本地KILL写入失败。操作系统终止、其他线程
错误与启动前检查不属于该局部修复；不能据此宣称所有重启原因或Redis根因已解决。

## 验证

测试使用真实`KillSwitch`、`LiveBroker`与隔离命名空间，故障传输分别模拟请求未送达、
已写入后回执超时，并同时拒绝Redis SET。两种情况均验证：本地KILL先于撤单、撤单尝试
只有一次、critical包含未知结果、后续循环不再tick、生产命名空间无写入。正常撤单返回的
原回归仍覆盖同一锁定语义。测试不连接生产Redis、不发订单/通知、不写生产状态。

生产发布、真实环境只读核验与自然运行观察分别记录在Issue，离线通过不替代它们。
