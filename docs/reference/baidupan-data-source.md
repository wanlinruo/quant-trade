安装方式：`npm install -g baidupan-cli`

### 2.2 凭证存放

凭证在 **`~/.baidupan-cli/config.json`**（权限 0600，目录 0700），**不在仓库内，也不要提交**。

字段结构（由 CLI 源码 `dist/index.mjs` 确认）：

```json
{
  "access_token":  "...",
  "refresh_token": "...",
  "app_key":       "...",
  "secret_key":    "...",
  "expires_at":    1791875756000
}
```

- `expires_at` 是**毫秒**时间戳。当前 token 有效期至 **2026-10-11**（30 天）。
- CLI 在 token 过期时会用 `refresh_token` 自动刷新并回写，正常无需干预。
- 授权 scope 为 **`basic netdisk`（全盘权限）**，不受「仅应用目录 `/apps/`」限制——已实测 `ls /` 能看到全部顶层目录。

### 2.3 重新授权流程（token 彻底失效时）

```bash
baidupan-cli auth -k <app-key> -s <secret-key>
```

- 应用在 <https://pan.baidu.com/union/console/applist> 创建，AppKey/SecretKey 由此获取。
- 回调地址留空，CLI 默认用 `oob`（带外）模式：浏览器授权后页面直接显示 code，**地址栏里没有**。
- CLI 会在终端交互式等待你粘贴 code。若拿到了 code 但交互提示已退出，可直接换取 token：

```bash
curl -s -G 'https://openapi.baidu.com/oauth/2.0/token' \
  --data-urlencode 'grant_type=authorization_code' \
  --data-urlencode 'code=<授权码>' \
  --data-urlencode 'client_id=<app-key>' \
  --data-urlencode 'client_secret=<secret-key>' \
  --data-urlencode 'redirect_uri=oob'
```

再按 2.2 的字段结构手工写入 `~/.baidupan-cli/config.json` 即可（`expires_at = now_ms + expires_in*1000`）。

## 3. 两个必须知道的坑

### 坑 1：`baidupan-cli list` 不分页，会静默截断

百度 `list` 接口单次上限 **1000 条**，而 `baidupan-cli` 不做翻页，
超过 1000 项的目录**只返回前 1000 条，且不报任何错**。

实测：`按企业CSV` 目录 CLI 只返回 1000 个文件（`000001.SZ.csv` .. `002376.SZ.csv`），
实际有 **5899** 个。

> **凡是列目录、清点文件，一律用 `scripts/baidupan.py`，不要用 `baidupan-cli list`。**
> 该脚本直调 REST 接口并按 `start` 翻页，已验证 `start=0/1000/2000/5000` 均正常返回。

### 坑 2：所有数据文件的第 1 行是广告行

CSV 和 xlsx **都**在真正表头之前插了卖家广告行，直接按常规方式读会把广告行当表头。

- **CSV**：带 UTF-8 BOM；第 1 行广告，**第 2 行才是表头**，第 3 行起是数据。
  用 `encoding="utf-8-sig"`，跳过 1 行。
- **xlsx**：sheet 名固定为 `data`；第 1 行广告，第 2 行标题（如 `A股日线数据（20260910）`），
  **第 3 行才是表头**，第 4 行起是数据。用 pandas 读需 `skiprows=2`。

已验证 1990 年和 2026 年的文件表头位置**完全一致**，无需逐年适配。

### 5.3 复权因子语义（已验证）

**结论：`复权因子` 就是 Tushare 的 `adj_factor`——以上市首日为基准（=1.0）的累计后复权因子。**

依据一（卖家自带的 `本地CSV查看器.html`，权威）：
- 列映射表里明写 `adj_factor: "复权因子"`
- 页面文案：「**后复权 ＝ 原价 × 当行复权因子**，不使用最新日期作基准。」
- 前复权：「基准取自全部已加载文件内**每股最新日期**」，代码为 `原价 × 当行因子 ÷ 基准日因子`

依据二（对真实数据独立验证，40 只随机股 + 000001 + 600519）：
- **40/40** 只股票首日复权因子 == `1.0` → 基准确为上市首日，因子累计递增
- 522 次因子变动事件中，`f(t)/f(t-1)` 与 `收盘(t-1)/昨收(t)` 的一致性：

  | 偏差区间 | 事件数 | 占比 |
  |---|---|---|
  | ≤0.02%（一致） | 396 | 75.9% |
  | 0.02%~0.1%（舍入） | 119 | 22.8% |
  | 0.1%~1% | 0 | 0.0% |
  | **>1%（实质不一致）** | **7** | **1.3%** |

**落库公式**：

```
后复权价 = 原始价 × 复权因子
前复权价 = 原始价 × 复权因子 ÷ 基准日复权因子     # 基准日自行指定，通常取最新交易日
```

> 前复权基准日必须**显式记录**。查看器用的是「该股在已加载文件中的最新日期」，
> 换一批文件基准就变——落库时不要沿用这个隐式行为，要把基准日固化并写进表。

#### ⚠ 已知缺陷：股改期 `昨收价` 与因子不自洽

上面 7 例 >1% 的实质不一致，**100% 落在 2005–2006 年股权分置改革期间**。
典型形态是 `昨收价` 完全没有做除权调整（价格比 = 1.0），而复权因子却跳变：

| 股票 | 日期 | 因子比 | 价格比 | 偏差 |
|---|---|---|---|---|
| 000603.SZ | 20060630 | 2.000000 | 1.000000 | 100.0% |
| 600429.SH | 20060419 | 1.420160 | 1.000000 | 42.0% |
| 600679.SH | 20060216 | 1.389783 | 1.000000 | 39.0% |
| 000063.SZ | 20051229 | 1.250170 | 1.000000 | 25.0% |

原因推测是**股改对价**被计入了 Tushare 因子、但未反映到 `昨收价` 列（**此归因未经证实**）。

**落库要求**：
1. 复权一律走 `复权因子` 列，**禁止**用 `昨收价` 反推复权比例——2005–2006 段会算错。
2. `涨跌幅（%）` 实测等于 `(收盘价/昨收价 - 1)*100`（000001 反例 1/8432、600519 反例 0/6001），
   即**基于未复权价**。跨除权日的收益率请自行用复权价重算，不要直接用这一列。
3. 上述 7 例来自 40 只样本，**不是全市场普查**。若策略回测覆盖 2005–2006，
   建议先对全量数据跑一遍同样的自洽性检查，把异常股票单独标记。

### 5.2 落库注意事项

1. **交易所后缀**：`按交易日` 的 xlsx 里 `股票代码` 没有交易所后缀，
   而 `按企业CSV` 的文件名里有（`000001.SZ`）。若落库需要带后缀的统一标识，
   由代码前缀确定性映射属于纯派生，可以做。映射表已用 `按企业CSV` 的 5899 个真实文件名
   全量校验，**零反例**：

   | 代码前两位 | 交易所 | 实测文件数 |
   |---|---|---|
   | `00` | SZ | 1640 |
   | `30` | SZ | 1448 |
   | `60` | SH | 1844 |
   | `68` | SH | 619 |
   | `83` | BJ | 3 |
   | `92` | BJ | 345 |

   注意：实测数据中北交所**只出现 `83` 和 `92` 两种前缀**（未见 `43`/`87` 等老三板代码）。
   映射要显式写死并加测试；遇到表中未出现的前缀应当**报错**，而不是猜一个交易所。
2. **数值单位**：成交量是「手」、成交额/市值是「万元」、股本是「万股」。
   落库时统一到基础单位（股 / 元）还是保持原单位，需要先定，然后写进 schema 注释。
3. **股票名称**随时间变化（ST 摘帽等），`按交易日` 布局天然保留了「当日名称」，
   这对 ST 状态的真值判定有用——不要用最新名称覆盖历史。
4. **1990–1991 年数据极稀疏**（1990 年仅 9 个交易日、每个文件 6 行左右），
   落库和校验逻辑要能容忍。
5. **xlsx 读取性能**：8723 个 xlsx 逐个用 openpyxl 读会比较慢，
   建议一次性转 parquet 落到 `warehouse/`，之后不再碰 xlsx。

## 6. 下载操作

### 6.1 推荐命令（当前优先级：按交易日）

```bash
# 全量下载 按交易日（8723 文件 / 3.52 GB）
python3 scripts/baidupan.py get \
  "/金融数据/每日日线/20260910/按交易日" \
  var/baidupan/按交易日 \
  --pattern '*.xlsx' --jobs 3
```

脚本行为：
- 递归遍历（**分页安全**），按远端相对路径在本地重建目录结构
- **幂等**：本地已存在且字节数一致则跳过，可随时中断重跑
- 先下到 `.part` 再校验大小、再改名，避免半截文件被当成完整文件
- 单文件失败自动重试 4 次（指数退避），每次重试重新申请 dlink（dlink 有时效）

> **`--jobs` 不要超过 3。** 实测并发 6 时服务端直接断开连接
> （`http.client.RemoteDisconnected`）。并发 3 + 重试实测 40/40 零失败。

### 6.2 速度与耗时预估

实测单文件下载约 **600 KB/s**（`--jobs 4` 并发下总吞吐会高一些，未精确实测）。

- `按交易日` 3.52 GB → **粗估 1–1.7 小时**
- 分钟行情 63.4 GB → 粗估 数十小时（这也是押后的原因之一）

> 开放平台 API 对非会员有限速。若速度不可接受，可考虑在网盘客户端里手动下载，
> 本文档的 schema 与落库结论同样适用。

### 6.3 断点与校验

重跑同一条 `get` 命令即可续传（按文件粒度）。全部下完后建议比对文件数：

```bash
find var/baidupan/按交易日 -name '*.xlsx' | wc -l   # 应为 8723
```

> 并优先只解压实际要用的周期（如只要 1min 就别解 5/15/30/60min）。

## 10. 数据源定位决策（2026-09-11，用户拍板）

**本付费数据源（余哈哈数据仓库）替换聚宽，成为历史日线的真值源。**

- **替换，不是并存**：不做与聚宽的交叉校验，聚宽相关的取数链路后续可以下线。
- **验真方式改为抽样检查**：由用户自行对该付费源做抽样验真（此前是用同花顺抽样验聚宽）。
- 这条决策**推翻了**本项目此前「聚宽是历史日线唯一真值源」的既定前提。
  `docs/superpowers/specs/2026-09-11-joinquant-truth-data-source-design.md` 及对应 plan
  中以聚宽为真值源的假设已失效，后续会话不要再按那份 spec 执行。

> 不变的硬约束：**禁止任何反推与填充**。拿不到的值一律落 `null`，
> 不填 0、不做前值填充、不做任何形式的估算——换了数据源，这条不松动。
